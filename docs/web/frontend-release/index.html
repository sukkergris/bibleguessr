Procedure

Application release

How a versioned frontend bundle and Docker images are released from one Git tag.

What a release is here

An application release creates two deliverables from one commit: a zip of the production frontend build, attached to a draft GitHub release, and Docker images for the API and nginx services. The zip is named after the frontend version. Both images currently use the fixed Docker tag 0.0.1.

The frontend and backend retain independent application versions. The fixed image tag is a known deployment-versioning limitation.

The version is one value

frontend/package.json holds the authoritative frontend version. Everything else derives from it — nothing is typed twice:

  • The meta tag in frontend/index.html , injected at build time by a transformIndexHtml plugin in frontend/vite.config.ts . The source file holds the placeholder 0.0.0 , which never survives a build.
  • The zip filename — bibleguessr-frontend-<version>.zip .
  • The git tag — frontend-v<version> .

This is deliberate rather than tidy. The meta tag used to be maintained by hand, and it drifted: package.json said 0.8.3 while the Nerd tab showed 0.7.2 , because nothing asserted the two agreed. Two tests now do — frontend/src/app-version.test.ts checks a fresh build, and the release script checks the artifact about to be packaged.

The local build steps

Taskfile.Release.yml holds the local frontend build chain. Running the bundle task also runs the verification ahead of it:

  • task release:frontend — runs the unit tests and the production build (both via the existing frontend: tasks), then verifies the result.
  • task release:bundle — packages the verified build as a zip.

Creating a Git tag and publishing the draft release are CI operations, not Task commands. This keeps the release authority in GitHub Actions, where the Docker Hub and GitHub credentials are available.

Verification is a step, not an assumption

build/fsx/VerifyFrontendArtifact.fsx reads frontend/dist/index.html and refuses to continue unless it matches package.json . It distinguishes four outcomes, each with its own message:

  • No dist/index.html — the build produced nothing.
  • No meta tag — the regex in vite.config.ts stopped matching.
  • Still 0.0.0 — injection did not run.
  • Version mismatch — dist/ is stale, left over from an earlier build.

The last one is the reason the script exists. dist/ is gitignored and can survive a branch switch, so without this check a bundle named 0.9.0 could contain 0.8.3 — a mislabelled artifact that nothing else would catch.

Each branch has been proven to fire by breaking the thing it guards and watching the script exit non-zero, per the testing rule in CLAUDE.md . A check that has never failed is not known to work.

What goes in the zip

The build output from frontend/dist/ , plus LICENSE and NOTICE.md from the repository root — nine files. NOTICE.md records the provenance of the bundled Bible text, which matters to anyone redistributing the artifact even though the text is public domain.

The zip's entries sit at its root rather than under a top-level folder, so it must be unpacked with an explicit destination: 

unzip bibleguessr-frontend-0.8.3.zip -d /usr/share/nginx/html/bibleguessr/
The -d is load-bearing

Without it, the files land in the current directory and overwrite whatever shares their names — in a host serving several sites, that means another site's index.html . A top-level folder inside the archive would make this safe regardless of the command; the trade was made deliberately, in favour of a predictable path for the image build. Anything consuming this artifact has to pass a destination.

Running it by hand

The frontend artifact can be checked locally without credentials: 

task release:bundle       # test, build, verify, package
unzip -l artifacts/bibleguessr-frontend-0.8.3.zip

artifacts/ is gitignored, so a bundle never reaches a commit.

Running it in CI

.github/workflows/release.yml first runs backend and frontend tests, then builds and publishes the Docker images, and finally calls task release:bundle. The frontend build remains defined once in the Taskfile rather than being repeated in YAML.

The workflow has two triggers:

  • A tag push matching frontend-v* — runs the tests, publishes the Docker images, bundles the frontend, and creates a draft release.
  • workflow_dispatch — a manual button that runs the same tests, publishes Docker images, and bundles the frontend, but skips the GitHub release step because github.ref is then a branch rather than a tag. Useful for checking that the build still works without producing a release.

The release step needs permissions: contents: write on the job. The repository's default workflow permission is read-only, and without the override the step fails with HTTP 403: Resource not accessible by integration . Granting it in the workflow rather than in the repository settings keeps the permission scoped to this job and visible next to the step that needs it.

Releases are created as drafts, so the assets can be inspected before anyone can download them. Publishing is a deliberate manual step in the GitHub UI.

Cutting a release

First update the frontend version when the frontend changed, and update the backend version when the backend changed. Then update scripts/ci/load-image-version.sh 's returned value — unlike the two application versions, this one is not conditional: both Docker images are rebuilt and republished on every tag push, so it needs a new value every release regardless of what changed. See Versioning for the full reasoning. Commit and push all changed version files before creating a tag whose version matches frontend/package.json: 

task release:bundle
git add frontend/package.json backend/Api/Program.fs scripts/ci/load-image-version.sh
git commit -m "release: frontend v0.8.3"
git push origin main
git tag frontend-v0.8.3
git push origin frontend-v0.8.3
gh run watch

Omit the two application-version files from the commit if their application didn't change — scripts/ci/load-image-version.sh stays in either way. The tag is the release trigger, so it must point at the already-pushed commit that is intended to ship. When the run finishes, the draft appears under Releases with the zip attached.

To undo a test release — the tag exists in three places, and deleting the release does not remove it: 

gh release delete frontend-v0.8.3 --yes --cleanup-tag  # release + remote tag
git tag -d frontend-v0.8.3                             # local tag

Consuming the artifact

The release zip is a downloadable frontend distribution. The current nginx Dockerfile does not consume it; it builds the frontend source from the same checkout as the API image. Both images are published with the same fixed tag.

The fixed image tag is overwritten by each publish, so it cannot identify a release or safely pin a deployment. Use the frontend GitHub release for versioned frontend distribution; container-image versioning remains a known limitation.

Implementation

Taskfile.Release.yml defines the frontend verification and bundle tasks. build/fsx/VerifyFrontendArtifact.fsx checks the built artifact and build/fsx/BundleFrontend.fsx packages it, both sharing helpers in build/fsx/lib/ . frontend/vite.config.ts injects the version at build time, and frontend/src/app-version.test.ts asserts that it matches.

.github/workflows/release.yml runs the chain in CI, and .github/README.md covers the workflow mechanics — how to watch a run, read the step icons, and what has already gone wrong.
