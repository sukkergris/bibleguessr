Feature

Congregation

A group game for a whole room: three or more players guess the same verses at the same time, each for their own score, with a live leaderboard anyone can put on a screen.

How a game goes

  1. In a private room, the host picks a game type (The Bible, Books or Chapters), a round count and a time limit, and presses Host a Congregation. A lobby opens.
  2. The other players in the room join the lobby, or don't. The host sees who has joined and a link for the spectator board.
  3. The host presses Start the game once enough players have joined. Only members who are connected at that moment take part, and nobody can join afterwards.
  4. Each round, everyone sees the same verse — in their own Bible — and guesses. The round is scored as soon as every connected player has guessed, or when the time is up.
  5. The scored round stays revealed for a short pause (the same moment for players and the spectator board), then the next verse follows. After the last round, everyone sees the final standings.

Rules

One activity per room

A room either hosts any number of independent duels, or is given over entirely to one Congregation — never both. The room's state is a single union, RoomActivity, so the mixed state can't even be represented:

  • Duels of GameSession list — zero or more one-vs-one games; empty means the room is idle.
  • Gathering of CongregationLobby — a lobby is open.
  • Congregating of CongregationGame — a Congregation is being played.

A lobby can only open in an idle room. Opening it withdraws every pending play request and empties the matchmaking queue. While a lobby is open or a game runs, nobody can challenge anyone or ask to be matched; the server refuses, and the room screen doesn't offer it in the first place.

Duels can run side by side. Before this union existed, the room had a single game slot, and a second duel silently replaced the first on the server — its players were left on a round that could never resolve. That is now impossible, and covered by backend/Tests/RoomActivityTests.fs and the "two matched duels" test in frontend/e2e/matchmaking.spec.ts.

A time limit is required

With twenty players, one idle phone must not stall everyone. A Congregation therefore always has a time limit, within the configured range. The lobby stores it as a plain TimeSpan rather than a TimeLimit, so "unlimited" can't be represented. The room screen disables Host a Congregation with the reason beside it while the time slider is at "No limit".

Who a round waits for

GameSession.allExpectedGuessed decides when a round can be scored early. A duel waits for both players, connected or not, as it always has. A Congregation waits only for participants who are connected and haven't left. If nobody fits that description — everyone is offline — the round is not ready; it waits for the timer instead of racing through every remaining round.

Every check is made inside the atomic room update that scores the round (see resolveRound's ResolveTrigger), so two near-simultaneous triggers — a last guess and the timer, say — can't score the same round twice or score the next round by mistake.

Leaving, disconnecting and coming back

  • Leaving the game (the Leave the game button) takes a player out; the others play on. The leaver keeps their score and stays on the leaderboard, marked "Left".
  • Losing the connection only stops the round waiting for that player. After the usual disconnect grace period they are removed from the room and count as having left.
  • Coming back — a reloaded page, a phone that was locked — means joining the room again under the same name while still marked disconnected. The newcomer then takes over the old seat: score, this round's guess and, for the host, the host role (Room.admit, GameSession.rebind). Duels keep their old behavior: the stale player is removed and the duel forfeited.
  • The last participant leaving ends the game with GameOver(Abandoned) and frees the room.
  • The host leaving the lobby cancels it. During the game the host has no special powers, so the game goes on without them.

Configuration

Read at startup by CongregationRules.fromConfig in backend/Domain/Lobby.fs. Each setting falls back to its default when unset; an impossible combination stops the server rather than producing a lobby nobody can start. The frontend reads the same values from GET /api/congregation/rules, so its controls can't drift from the server's.

Setting Default Meaning
Congregation:MinPlayers 3 Connected members needed to start. At least 2 (handy for trying it out alone).
Congregation:MaxPlayers 20 Members a lobby takes.
Congregation:MinTimeLimitSeconds 10 Shortest time limit per verse.
Congregation:MaxTimeLimitSeconds 60 Longest time limit per verse (the slider's own maximum).
Congregation:RevealSeconds 5 How long a scored round stays revealed before the next verse.

The round count uses the same 3–10 range as every other mode (CongregationLobby.minRoundCount, maxRoundCount).

Hub API

Method Who Effect
OpenCongregation(gameType, roundCount, timeLimitSeconds) Anyone in an idle private room Opens a lobby with the caller as host.
JoinCongregation() / LeaveCongregation() Room members Join or leave the lobby. The capacity check happens inside the atomic update.
CancelCongregation() / StartCongregation() The host Close the lobby, or start the game with the connected members.
ForfeitGame() A participant For a Congregation: leave the game, keeping the score.
WatchRoom(roomCode) / UnwatchRoom(roomCode) Anyone The spectator board — see its own page.

Events, besides the usual RoundStarted, RoundScored and GameOver:

  • RoomActivityChanged(RoomActivityView) — to the room, on every change of what the room is doing (a duel starting or ending, the lobby changing, the game starting, someone leaving it), and to each player right after they join. It is also how a late joiner learns who is busy in a duel.
  • LeaderboardUpdated(LeaderboardSnapshot) — to the room and the spectators, whenever the board changes: a guess (who, never what), a departure, a scored round, the end.
  • GameOver now carries (gameId, scores, participants, reason), with the new reason Abandoned.

Implementation

Domain. backend/Domain/Lobby.fs holds the rules and the lobby; backend/Domain/Game.fs generalizes GameSession from two players to Participants with a Format (Duel or Congregation of host), so duels and Congregations share scoring, the timeout sweep and resolveRound. RemovalImpact describes what removing a player did to the room's games, and every removal path broadcasts it the same way. backend/Domain/Leaderboard.fs projects the board.

Hub. backend/Api/GameHub.fs. A Congregation round is only scored by resolveRound; RoundTimeoutService moves it on once the reveal pause is over (advanceRevealedRound), so everyone sees the reveal for the same length of time. A duel still advances immediately.

Frontend. frontend/src/congregation/. The room screen owns a CongregationController that hears every Congregation event from the moment the player joins and folds it into a CongregationState with pure functions (congregation-state.ts). The lobby, game and results components only render what they're given, so none of them can miss an event that arrived before it mounted. Unlike the duel screen, the Congregation game has no flashing final countdown — it's often played around one shared screen.
