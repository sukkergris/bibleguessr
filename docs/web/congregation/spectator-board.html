Feature

Spectator board

The live leaderboard of a room's Congregation, for a projector or TV — opened by anyone with the link, with no name and no joining.

Opening it

The link is https://<site>/#/watch/<room code>. The host sees it in the lobby, and players who aren't taking part get a Watch the live leaderboard link while the game runs. It is a hash route (frontend/src/congregation/watch-route.ts), so the web server needs nothing special: the page loads as usual, bg-app reads the room code from the hash and shows the board in place of the usual screens.

The board follows the room through its whole life: "No Congregation yet", the lobby filling up, the game, and the final standings — which stay up until the next lobby opens, so a projector that reloads after the game still shows them.

What a spectator can see

Spectators get exactly one thing from the server: the LeaderboardSnapshot (backend/Domain/Leaderboard.fs) — as the return value of WatchRoom and as LeaderboardUpdated on every change. It holds names, scores, ranks, whether each player has guessed this round, and the round's state.

  • Never the verse while it is being guessed. BoardRound.Guessing has fields for the round number and the deadline only — there is nowhere to put a reference, so the board can't leak one by mistake. Only Revealed, after the round is scored, carries it.
  • Never what anyone guessed — only whether they have.
  • Never verse text. The server never sends text to anyone (see the data-security rule in CLAUDE.md), and the board's code can't even reach a Bible source: the architecture test forbids its files from importing bible-sources/, the verse card or the guess form.

Why spectators have their own group

Every room event goes to the room's SignalR group, and RoundStarted must carry the reference of the round being guessed — each player's client needs it to show the verse from their own Bible. A spectator in that group would receive it too. So WatchRoom adds the connection to a separate group, <code>:spectators, and never registers it as a player or adds it to the room group. Every player-only hub method therefore answers a spectator with "You haven't joined a room".

The guarantee covers the spectator channel only

Players do receive the reference of the round they are guessing — they need it, and a determined player can see it in the browser's developer tools. That is the same trust model as duels. The board's guarantee is that a screen everyone in the room can see doesn't give the answer away.

The leak is tested twice: backend/Tests/LeaderboardTests.fs serializes a board mid-round with the hub's own JSON converter and checks it holds no reference, and frontend/e2e/congregation.spec.ts checks every WebSocket frame the spectator page received before the first reveal.

SignalR forgets group membership when a connection reconnects, so the board calls WatchRoom again from onReconnected.

Accessibility

  • The leaderboard is a native <table> with a caption and column headers (leaderboard-table.ts). Status is written out — "Guessed", "Waiting", "+110", "No guess", "Left", "(offline)" — never shown by color alone.
  • One role="status" live region speaks only the moments a sighted viewer would notice: the lobby opening, the start, each scored round with the leader, and the winner (board-announcer.ts). Individual guesses and the ticking clock are never announced; with twenty players they would drown everything else out. The countdown is aria-hidden.
  • Type sizes use clamp() to read across a room on a big screen and still fit a phone, and there is no motion to reduce.
