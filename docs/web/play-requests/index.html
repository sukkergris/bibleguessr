Feature

Start a game from chat

Choose a game type, then click another online player's name to challenge them — they see the game type and can accept or deny, and you can withdraw your request any time. Specs: docs/SCRUM/Feature.StartMPGame.md (send/see/withdraw) and docs/SCRUM/Feature.RequestToStartMPGame.md (game type + accept/deny).

Builds on Multiplayer rooms & chat — read that first if the hub/room basics aren't familiar yet.

What it does

  • Before challenging anyone, pick a game type — All verses, Books, or Chapters (same three types and selectors as singleplayer setup).
  • Click another player's name in the roster → sends them a play request carrying that game type.
  • The receiver sees every request addressed to them, with the game type, below the chat window.
  • The receiver can accept or deny a request.
  • A sender can only ever have one outstanding request at a time, and can withdraw it.
Accept doesn't start a game — yet

Accepting only resolves the request (removes it, tells both clients). Actually starting a synced game — picking a shared verse, syncing rounds between the two players — depends on round sync, which isn't built yet (see Multiplayer rooms). Wiring that up is future work; this feature stops at "both players know the challenge was accepted."

REPLACE semantics

Sending a new request while one is already pending doesn't error — it silently retargets. Clicking a different player just supersedes your old outstanding request with a new one, no explicit withdraw-first step required. This mirrors Discord/Steam-style single-target invites, and avoids an extra error-and-recovery UI path for what's usually just a misclick or a change of mind.

Domain model

backend/Domain/Game.fs

type GameType =
    | AllVerses
    | Books of string list
    | Chapters of Map<string, int list>

type PlayRequest =
    { FromPlayerId: PlayerId
      FromPlayerName: string
      ToPlayerId: PlayerId
      GameType: GameType
      SentAt: DateTimeOffset }

GameType mirrors the shape of the existing /api/verses/random restriction query params (book/bookChapter, see backend/Api/Program.fs and Verse.matchesRestriction) rather than inventing new vocabulary — it's the same all/books/chapters split as singleplayer's SetupScope.

Stored per-room on Room.PendingRequests — there's no cross-room player identity anywhere in this codebase (a PlayerId only ever means something within the room that minted it), so a global request store would invent structure nothing else needs.

Pure functions on the Room module — the same "pure domain function, thin hub wrapper" pattern the Scoring module already used, which is what makes all of this unit-testable without any SignalR mocking:

Function Behavior
sendPlayRequest request room Drops any existing request from the same sender, then adds the new one. This is the REPLACE semantics.
withdrawPlayRequest fromPlayerId room Removes that sender's pending request, if any. No-op otherwise.
acceptPlayRequest fromPlayerId toPlayerId room Removes the matching (sender, target) request, if it still exists. No-op otherwise — the sender may have withdrawn or retargeted just before the click landed.
denyPlayRequest fromPlayerId toPlayerId room Same as acceptPlayRequest — the two only differ in which hub event the caller broadcasts afterwards.
pendingRequestsFor toPlayerId room Filters requests addressed to one player.

Hub protocol

Method / Event Direction Payload
SendPlayRequest(toPlayerId, gameType) client → server target's PlayerId string + the chosen GameType
WithdrawPlayRequest() client → server —
AcceptPlayRequest(fromPlayerId) client → server the challenger's PlayerId string
DenyPlayRequest(fromPlayerId) client → server the challenger's PlayerId string
PlayRequestReceived server → room group the full PlayRequest record
PlayRequestWithdrawn server → room group the withdrawing sender's PlayerId string
PlayRequestAccepted server → room group (fromPlayerId, toPlayerId) string pair
PlayRequestDenied server → room group (fromPlayerId, toPlayerId) string pair, same shape as PlayRequestAccepted

SendPlayRequest validates the target is still in room.Players before creating the request ("Error", "That player is no longer in the room" otherwise). Accept/deny are forgiving no-ops if the request they name is already gone (withdrawn or retargeted).

Broadcast, not routed

Every play-request event goes to the whole room group, not just the parties involved — every client just ignores events not addressed to them (see the frontend section below). This is because RoomStore has no PlayerId → connectionId reverse index today, and building one just for this felt like more than the change needed. It's explicitly not a privacy guarantee — a determined client could see it via devtools regardless — just a pragmatic simplification for a hobby project's trust model.

Frontend

frontend/src/components/game-type-select.ts (<bg-game-type-select>) sits above the players list in the room screen and lets the challenger pick All/Books/Chapters, reusing the same <bg-book-selector>/ <bg-chapter-selector> components singleplayer setup uses. It fires game-type-changed; bg-room-setup.ts keeps the current selection and turns it into a GameType (via frontend/src/game-type.ts's gameTypeFromRestriction) each time a player is challenged.

frontend/src/components/play-requests.ts (<bg-play-requests>) is a "dumb" view component — kept apart from chat-panel.ts since it's a distinct concern with its own event surface, matching the spec's "a list below the chat window." It shows incoming requests ("X wants to play", plus the game type via describeGameType) with Accept/Deny buttons, and, if the viewer has one outstanding, "Request sent to Y" with a Withdraw button. It fires accept-play-request/deny-play-request/withdraw-play-request events.

The click target for sending a challenge is the players list only, not inline chat message sender names — a stable, deliberate click target, versus making every scrolling chat message clickable and risking accidental invites. chat-panel.ts fires player-selected (detail = clicked player's id) when you click someone else's name; your own name renders without the click affordance.

bg-room-setup.ts owns playRequests: PlayRequest[] (addressed to me) and sentRequestToId?: string (my own outstanding request). On PlayRequestReceived: if the sender is me, it's an echo of my own send/retarget, so it updates sentRequestToId instead of appending to the list; otherwise, if it's addressed to me, it replaces any existing entry from that sender (mirroring REPLACE) and appends. On PlayRequestAccepted/PlayRequestDenied, the named request is dropped from playRequests, and sentRequestToId clears if it was mine.

Verify it

  • Backend: backend/Tests/RoomTests.fs and backend/Tests/PlayRequestTests.fs — REPLACE semantics, independent senders to the same target, isolated withdrawal, accept/deny resolving the matching request only.
  • Frontend unit: frontend/src/game-type.test.ts — building a GameType from a chosen scope/restriction, and describing one for display.
  • End-to-end: frontend/e2e/play-request.spec.ts (send → receive → withdraw) and frontend/e2e/play-request-accept-deny.spec.ts (send → accept, send → deny) — two browser contexts each, against live dev servers.
