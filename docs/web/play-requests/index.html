Feature

Start a game from chat

Click another online player's name to invite them — they see it in a list below the chat window, and you can withdraw it any time. Spec: docs/SCRUM/Feature.StartMPGame.md.

Builds on Multiplayer rooms & chat — read that first if the hub/room basics aren't familiar yet.

What it does

  • Click another player's name in the roster → sends them a play request.
  • The receiver sees every request addressed to them in a list below the chat window.
  • A sender can only ever have one outstanding request at a time.
  • The sender can withdraw their pending request.
Deliberately out of scope

There's no accept/decline. The spec only asks for send/see/withdraw, and actually accepting a request would mean starting a synced game — which depends on round sync, which isn't built yet (see Multiplayer rooms). Building a fake accept button now would just need reworking later, so a request simply sits visible until it's withdrawn or superseded.

REPLACE semantics

Sending a new request while one is already pending doesn't error — it silently retargets. Clicking a different player just supersedes your old outstanding request with a new one, no explicit withdraw-first step required. This mirrors Discord/Steam-style single-target invites, and avoids an extra error-and-recovery UI path for what's usually just a misclick or a change of mind.

Domain model

backend/Domain/Game.fs

type PlayRequest =
    { FromPlayerId: PlayerId
      FromPlayerName: string
      ToPlayerId: PlayerId
      SentAt: DateTimeOffset }

Stored per-room on Room.PendingRequests — there's no cross-room player identity anywhere in this codebase (a PlayerId only ever means something within the room that minted it), so a global request store would invent structure nothing else needs.

Pure functions on the Room module — the same "pure domain function, thin hub wrapper" pattern the Scoring module already used, which is what makes all of this unit-testable without any SignalR mocking:

Function Behavior
sendPlayRequest request room Drops any existing request from the same sender, then adds the new one. This is the REPLACE semantics.
withdrawPlayRequest fromPlayerId room Removes that sender's pending request, if any. No-op otherwise.
pendingRequestsFor toPlayerId room Filters requests addressed to one player.

Hub protocol

Method / Event Direction Payload
SendPlayRequest(toPlayerId) client → server target's PlayerId as a string
WithdrawPlayRequest() client → server —
PlayRequestReceived server → room group the full PlayRequest record
PlayRequestWithdrawn server → room group the withdrawing sender's PlayerId string

SendPlayRequest validates the target is still in room.Players before creating the request ("Error", "That player is no longer in the room" otherwise).

Broadcast, not routed

PlayRequestReceived goes to the whole room group, not just the target — every client just ignores requests not addressed to them (see the frontend section below). This is because RoomStore has no PlayerId → connectionId reverse index today, and building one just for this felt like more than the change needed. It's explicitly not a privacy guarantee — a determined client could see it via devtools regardless — just a pragmatic simplification for a hobby project's trust model.

Frontend

frontend/src/components/play-requests.ts (<bg-play-requests>) is a new, separate "dumb" view component — kept apart from chat-panel.ts since it's a distinct concern with its own event surface, matching the spec's "a list below the chat window." It shows incoming requests ("X wants to play") and, if the viewer has one outstanding, "Request sent to Y" with a Withdraw button, firing a withdraw-play-request event.

The click target is the players list only, not inline chat message sender names — a stable, deliberate click target, versus making every scrolling chat message clickable and risking accidental invites. chat-panel.ts fires player-selected (detail = clicked player's id) when you click someone else's name; your own name renders without the click affordance.

bg-room-setup.ts owns playRequests: PlayRequest[] (addressed to me) and sentRequestToId?: string (my own outstanding request). On PlayRequestReceived: if the sender is me, it's an echo of my own send/retarget, so it updates sentRequestToId instead of appending to the list; otherwise, if it's addressed to me, it replaces any existing entry from that sender (mirroring REPLACE) and appends.
