Feature

Report abuse

A always-available way for a player to report abusive, harassing, or otherwise unsafe behavior, delivered to the application owner by email.

User flow

  1. A shield button sits in the bottom-left corner of every screen, labelled Report abuse.
  2. Selecting it replaces the current view with the Report abuse form, remembering what was underneath.
  3. The reporter describes what happened (required) and may optionally name the reported player and give a reply address.
  4. Sending disables both actions until the request settles, so at most one report is submitted.
  5. Success shows a confirmation; failure keeps the form and its contents so the report can be retried.
  6. Cancel returns to the previous screen without sending anything.

Opening and closing

The sticky button is a toggle: it opens the report view when closed, and closes it when open. Closing through the icon is the same path as Cancel — no report is submitted and unsent text is discarded. Its accessible name and tooltip describe the action it will perform (Report abuse or Close report abuse), and it exposes aria-expanded.

While a report is being sent the toggle is disabled, so it can never tear the view down mid-request or produce a second submission. Focus moves into the view on open and returns to the toggle on close.

What is and isn't sent

Only what the reporter types. Nothing is captured automatically, so a report can never carry uploaded verse text, game state, or another player's data unless the reporter deliberately writes it. Reports are not written to browser storage, the Bible cache, or the game session.

The form warns against including passwords, payment details, or other sensitive personal data, and the optional reply address is used only to answer the report.

Delivery and abuse prevention

Reports go to POST /api/abuse-reports — deliberately separate from the Bible-file upload report endpoint, so neither contract has to bend to accommodate the other. The endpoint reuses the existing SMTP configuration and sends with the subject BibleGuessr: Abuse report.

Every field is treated as untrusted input and HTML-encoded before it goes into the email body. The reporter's address is never used as the sender: the configured, relay-authorised From address is kept, and their address is attached as Reply-To instead. An unparseable reply address is dropped rather than blocking delivery of the report itself.

The endpoint shares the bug-report endpoint's two rate limiters — one per caller IP, one global — because both protect the same single mail relay. Validation runs before any mail is attempted, so malformed or oversized requests cost the relay nothing and return 400; rate limits return 429; an SMTP failure returns 502, which the form presents as retryable. Delivery failures are logged without report content or contact details.

Accessibility behavior

The sticky control is a real <button> with an aria-label, so it has an accessible name rather than relying on the icon. It is positioned clear of mobile safe-area insets and sits in the one corner that does not overlap the countdown, chat, or form fields.

Every field has a persistent label and an associated hint or validation message. A rejected submission sets aria-invalid, announces the problem with role="alert", and moves focus to the field at fault. Sending, success, and failure are announced through role="status". Invalid state is signalled by border weight as well as color. Opening the report moves focus into the view; cancelling returns it to the report button.

Implementation

backend/Domain/AbuseReport.fs holds the report type and a pure validate function that trims input, rejects empty or whitespace-only descriptions, treats blank optional fields as absent, and enforces maximum lengths. Rejections are a typed union so the API layer owns the wording and status codes.

backend/Api/MailSender.fs builds and sends the email; backend/Api/Program.fs exposes the endpoint. frontend/src/components/report-abuse.ts owns the form, its explicit submit-state model, and the duplicate-submit guard; frontend/src/components/bg-app.ts owns the sticky button and the return-to-previous-view behavior.

Validation, trimming, and the length limits are covered by backend/Tests/AbuseReportTests.fs. Rendering, navigation, validation, keyboard access, duplicate-submit prevention, successful delivery, delivery failure, and rate limiting are covered by frontend/e2e/report-abuse.spec.ts.
