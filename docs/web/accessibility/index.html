Accessibility

What is enforced automatically, what was fixed, and what only a person can check.

Enforced on every test run

An audit walks the rendered page, including Lit shadow roots — a plain document.querySelectorAll sees almost nothing here, so source-level attribute checks would be misleading. It runs across the home, setup, game, report, bug, multiplayer pre-join and room screens, and fails the suite if either rule breaks:

  • Every interactive control has an accessible name.
  • No form field depends on a placeholder for its name.

title is deliberately not accepted as a name: it is unreliable across screen readers and invisible to touch users.

What it caught

Roster players were clickable list items — no tab stop, no interactive role — so a keyboard-only player could chat but could not challenge anyone. They are real buttons now. The connection dot was named only by a title; the chat and room-code fields only by their placeholders. The Bible-file picker was named by the whole drop-zone sentence rather than by what it is.

What is announced

Round changes, guess feedback and score reach a screen reader through one live region, derived from a single string so each change is announced exactly once and never twice by two regions. Verse-loading failures are alerts rather than status updates, because they interrupt: the player cannot continue until the error is dealt with. File selecting, parsing, ready and failed states are announced, without progress numbers that would re-announce on every chapter.

Names, not identifiers

Cached Bible files are shown by filename with their extension, never by the cache fingerprint. That holds through a named fileNameFromFingerprint beside the function that builds the fingerprint, rather than an inline split that only worked by coincidence of field order.

Background tokens used as foregrounds

The theme tokens are named for meaning, not appearance, and the failure mode that follows from getting one wrong is unusually invisible. Styling a control with color: var(--surface-raised) paints its label in the colour of the surface behind it: white on white in the light theme (1.00:1), near-black on near-black in the dark theme (1.22:1). The text is still in the DOM, still has an accessible name, and still passes the audit above — it simply cannot be seen.

This has now been found twice. The first time it was the translation-source mode switch; the fix left a comment, but three sibling controls carrying the same three-line block were missed — the game-type scope pills (All / Books / Chapters) and the cached-translation entries in both setup screens. An unselected control sits on the page surface, so it takes --text; only a control that paints its own filled background takes a paired foreground such as --accent-text.

Because neither an accessible-name audit nor a unit test can see it, this is covered by computed-colour checks that read each control's foreground against the background actually painted behind it — resolved by walking up through shadow hosts, since the controls themselves are transparent. Both specs assert only the unselected state; the selected pill is --accent-text on --accent, which is 4.39:1 in the dark theme — a separate pre-existing defect in the token itself, affecting every accent-filled control app-wide.

What automation cannot settle

Contrast is only partly automated — the computed-colour checks above cover specific controls that regressed, not the palette as a whole. That, whether announcements actually read well aloud, focus order judged as a whole, and behaviour at 200% zoom in a real browser all still need a person. Those live in docs/SCRUM/TODO/Checklist.ManualAccessibilityPass.md. Passing the automated audit is not a claim of WCAG conformance.

Implementation

frontend/e2e/helpers/a11y.ts holds the audit; frontend/e2e/accessibility.spec.ts runs it per screen and covers keyboard access, announcements, zoom and touch targets. frontend/e2e/mode-switch-contrast.spec.ts and frontend/e2e/game-type-contrast.spec.ts hold the computed-colour checks.
