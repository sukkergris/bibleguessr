Feature

Unique player names

Two players in the same room can't have the same name. Joining under a name that's already in use is rejected with a clear message — unless the name belongs to a disconnected player, in which case it's freed up so a reconnecting player isn't locked out of their own name. Spec: docs/SCRUM/Featue.UniquePlayerName.md (filename typo preserved as it exists on disk).

Builds on Multiplayer rooms & chat and Player presence — this feature's whole "disconnected vs. connected" distinction is presence's DisconnectedPlayers bookkeeping, and its stale-removal path reuses the same removal machinery presence's cleanup sweep uses.

What it does

  • Each player must have a unique name within a room (case-sensitive — see below).
  • Trying to join with a name already in use is rejected outright, with a clear on-screen message asking for another name.
  • Reconnecting under your own name (refresh, brief network drop) isn't treated as a duplicate — it silently frees up the old, now-disconnected entry so the rejoin succeeds.
  • Each player only ever has one name in the chat — there's exactly one Player record per join, and the roster/chat both render Player.Name directly, so there's no separate "display name" to drift out of sync.

The problem this solves

Without this, two players could both be "Alice" in the same room — the roster and chat log would have no way to tell them apart, and clicking one to send a play request would be ambiguous about which "Alice" you meant. The fix has two halves that have to work together: reject a genuine collision, but never punish someone for simply losing and re-establishing their own connection (which player presence already treats as a graceful, expected event, not a departure).

Case-sensitive by deliberate choice

Name matching here is case-sensitive — "Alice" and "alice" are different names and can coexist in the same room. That's a deliberate product decision for this feature specifically, not an oversight: it goes against this codebase's usual OrdinalIgnoreCase convention for name-ish matching (book names, for instance — see Verse.matchesRestrictionByNumber), and against a case-insensitive match being the safer, more usual default for this kind of check. It was chosen anyway for this feature and is pinned down by a dedicated test (see backend/Tests/UniquePlayerNameTests.fs) so a future refactor doesn't "helpfully" fix it into case-insensitivity by accident.

Domain model

backend/Domain/Game.fs

/// Checked before letting a new player join under `name` — see
/// docs/SCRUM/Featue.UniquePlayerName.md. Rejects (Error) if `name`
/// (case-sensitive) is already held by a player who's currently
/// CONNECTED. If it's held by a DISCONNECTED player instead — their
/// own dropped connection reconnecting under the same name, most
/// likely — that stale entry (and its pending requests/active game,
/// same as removeStaleDisconnections) is removed first so the
/// rejoin succeeds cleanly instead of either being rejected as a
/// duplicate or leaving a ghost entry behind.
let prepareJoin (name: string) (room: Room) : Result<Room, unit> =
    match room.Players |> List.tryFind (fun p -> p.Name = name) with
    | None -> Ok room
    | Some existing when room.DisconnectedPlayers.ContainsKey existing.Id ->
        let updated, _ = removePlayers (Set.singleton existing.Id) room
        Ok updated
    | Some _ -> Error ()

prepareJoin is built directly on top of a small refactor to the presence-cleanup code: the old, single-purpose removeStaleDisconnections (the periodic sweep's entire job — remove everyone disconnected before a cutoff) had its actual player-and-related-state removal logic pulled out into a private removePlayers (idsToRemove: Set<PlayerId>) (room: Room) : Room * PlayerId option helper. removeStaleDisconnections now just computes the stale id set and delegates; prepareJoin calls the same helper with a one-element set (the single stale player whose name collided). Both call sites get identical guarantees for free: the removed player is dropped from Players and DisconnectedPlayers, any play request naming them (sent or received) is dropped from PendingRequests, and if they were part of the room's ActiveGame that game ends too — with the surviving opponent's id returned so the caller can broadcast GameOver(Forfeited) for them, exactly as if the grace-period sweep had caught them.

What happens on join

Situation Result
Name isn't held by anyone in the room Immediate join — Ok room, unchanged.
Name is held by a currently connected player Rejected — Error (). No player is added; the caller alone is told why.
Name is held by a currently disconnected player The stale entry is silently removed first (dropped from the roster, its pending play requests, and its active game if any — with PlayerLeft/GameOver(Forfeited) broadcast to everyone else exactly like the periodic sweep would), then the join proceeds normally under a brand-new PlayerId.

Hub wiring

backend/Api/GameHub.fs

GameHub.JoinExistingRoom(room, playerName) is the shared join path both JoinRoom (room code) and JoinWorldChat (the always-open World chat room) delegate to — they differ only in how they find/create the room. It calls Room.prepareJoin first, before doing anything else:

  • On Error (): sends the caller (only) an "Error" event with the message "That name is already taken in this room. Please choose another.", then failwith "Name already taken" — no PlayerJoined is broadcast, and no player is added.
  • On Ok preparedRoom: if a stale player was actually removed (detected by comparing preparedRoom.Players.Length against the original room's), the hub broadcasts PlayerLeftEvent for that player to the whole room group — and, if they were part of an ActiveGame, also broadcasts GameOverEvent naming the surviving opponent with reason Forfeited — the same two broadcasts PlayerCleanupService's periodic sweep sends for exactly this situation. Only then does the new Player get created, added, and the usual PlayerJoined/ChatHistory/RoomPlayers sequence proceed.
A bug found and fixed while building this feature: EnableDetailedErrors

Rejecting a hub call with failwith "..." alone isn't enough for the client to ever see the message. By default, ASP.NET Core SignalR treats a hub method's thrown exception as a server-internal detail and hides it — the client's rejected invoke only ever sees a generic "An unexpected error occurred invoking '...' on the server.", with the real reason swallowed. Building this feature surfaced that gap, since "That name is already taken..." is exactly the kind of message a player actually needs to see. The fix, in backend/Api/Program.fs, is AddSignalR(fun options -> options.EnableDetailedErrors <- true) — deliberately safe here because every message thrown this way (across this whole hub, not just this feature) is a hand-written, user-facing validation message, never raw exception/stack-trace detail.

That alone wasn't the whole fix. The frontend's join handlers (frontend/src/components/bg-room-setup.ts, _onCreateRoom/_onJoinRoom/_onJoinWorldChat) each subscribe to a server-pushed onHubError event inside _enterRoom, before awaiting the join invoke — so the real "Error" message (now reaching the client thanks to EnableDetailedErrors) typically lands in this.error slightly before the invoke's promise itself rejects. Each catch block used to unconditionally overwrite this.error with a generic fallback ("Failed to join the room.", etc.) once the invoke rejected — clobbering the correct, specific message that had just arrived. The fix was changing that overwrite to this.error ?? (this.error = err instanceof Error ? err.message : 'Failed to join…'): only fall back to the generic message if nothing more specific got there first. This is a real, non-obvious ordering bug (message arrives, then gets stomped moments later) rather than a feature detail — worth knowing about since the same pattern (server-pushed error race-arriving just ahead of the invoke rejection) will bite any future hub call that reports errors this way.

Leaving a room voluntarily — Room.leave / LeaveRoom

A bug found after shipping: rejoining your OWN room, same tab, was broken

Once this feature shipped, "That name is already taken" started firing against a player's own still-live entry: click "← Home", come back into Multiplayer, try to rejoin the exact room you were just in under your own name — rejected, even though nothing else was actually using that name. The cause: the SignalR hub connection is a page-lifetime singleton (see Multiplayer rooms) that's never stopped on navigation — going Home only ever reset local UI state (frontend/src/components/bg-app.ts's _onGoHome, and frontend/src/components/bg-room-setup.ts's _onLeaveRoom) — so the old Player stayed fully connected server-side for as long as the tab stayed open. Room.prepareJoin was working exactly as designed; there was simply no hub method that ever told the server "I'm leaving" in the first place.

Room.leave (playerId) (room) — new in backend/Domain/Game.fs, built on the same private removePlayers helper prepareJoin and removeStaleDisconnections already share — removes a player immediately and unconditionally, no grace period: a deliberate, in-the-moment departure isn't a dropped connection that might recover, so there's no reason to leave a stale entry around the way a disconnect does. Drops their pending play requests and ends their active game (freeing the opponent) the same way the other two removal paths do, returning (updatedRoom, forfeitedOpponent: PlayerId option).

GameHub.LeaveRoom() — new in backend/Api/GameHub.fs — calls it for the caller, broadcasts PlayerLeft, and (mirroring ForfeitGame's pattern exactly) broadcasts GameOver(Forfeited) with real final scores if they were mid-game. A no-op if the caller isn't in a room. Deliberately does not stop the underlying connection itself — the same connection goes on to join whatever room the player picks next.

Frontend

The multiplayer "choose" screen's join flow needed no changes once the two backend-side fixes below were in place: the hub now actually rejects a colliding name with a real message, that message now reaches the client (EnableDetailedErrors), and the catch block now preserves it instead of overwriting it with a generic fallback (the precedence fix). The rejected join simply surfaces as this.error, rendered the same way any other join failure already was.

frontend/src/signalr-client.ts's new leaveRoom() wrapper is called from both places a player actually leaves — bg-room-setup.ts's _onLeaveRoom ("Back to chat selection", within the same mounted component) and its disconnectedCallback (fired when bg-app.ts's "← Home" button unmounts <bg-room-setup> wholesale — a genuinely different removal path from the button click, which needed its own fix). Both are fire-and-forget, matching this file's other best-effort hub calls: the local teardown happens either way, since the player is leaving regardless of whether the server call succeeds.

Verify it

  • Backend: backend/Tests/UniquePlayerNameTests.fs — 9 scenarios covering Room.prepareJoin: succeeds when the name is free; rejects a name held by a connected player; is case-sensitive ("Alice" vs. "alice" can coexist); allows an unrelated new name alongside an existing player; succeeds and removes a disconnected player of the same name; also drops that stale player's disconnection bookkeeping; also drops their pending play requests; leaves other connected players and their own requests untouched when only replacing a stale one; and ends the stale player's active game, freeing their opponent. backend/Tests/LeaveRoomTests.fs — 8 scenarios covering Room.leave: removes the player; no-op for a stranger; frees their name for an immediate rejoin (no grace period); drops disconnection bookkeeping and pending requests; leaves others untouched; ends an active game and reports the surviving opponent.
  • End-to-end: frontend/e2e/unique-player-name.spec.ts — joining World chat with a name already in use by a connected player is rejected with a visible "already taken" message (and the rejected player never actually enters the room, while the original player is unaffected); going Home and back into Multiplayer under the SAME name in the SAME tab (no connection drop at all) succeeds — the exact reported bug above, reproduced and fixed; and reconnecting under your own name after a real connection drop (closing the old browser context, rejoining under the identical name in a fresh context) succeeds, with no "already taken" message shown.
