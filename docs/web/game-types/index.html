Architecture

Game types

Each game type (The Bible, Books, Chapters) is its own bounded context. A game type owns its setup UI, which verses it draws, what the guess form offers, how guesses score and how it travels to the server. Game types never depend on each other, so one can change a lot without affecting the others.

Layout

frontend/src/
  shared-kernel/            vocabulary every game type may use
    bible.ts                Verse, VerseReference, Guess, VerseSource, VerseRestriction
    book-numbers.ts         book name ⇄ book number
    game-type-wire.ts       the GameType JSON shared with the backend
    guess-constraint.ts     what the guess form may offer
    scoring.ts              the standard singleplayer scoring rule
  game-types/
    game-type-definition.ts the contract every game type implements
    the-bible/              one folder per game type: definition, setup UI, tests
    books/
    chapters/
    registry.ts             the ONLY module that knows every game type
  architecture.test.ts      enforces the rules below (and those of shared-ui/, bible-sources/ and social/)

backend/Domain/
  Scoring.fs                           shared kernel: Guess, TimeLimit, the standard scoring rules
  GameTypes/
    TheBible.fs  Books.fs  Chapters.fs one module per game type: verse restriction, scoring rule
    GameType.fs                        the wire DU + dispatch, the only place that knows all three

Rules

  • A game type imports only from its own folder, the shared kernel and the contract (game-type-definition.ts). It never imports from another game type or from the app shell.
  • The shared kernel imports only from itself. It must never know about a particular game type.
  • The rest of the app (components, bg-app.ts, multiplayer) reaches game types only through registry.ts, and never branches on which game type is in play.
  • Backend: a module in Domain/GameTypes/ never references a sibling module. Only GameType.fs composes them.

These rules are tests, not conventions. frontend/src/architecture.test.ts reads every file's imports, and backend/Tests/GameTypeIsolationTests.fs reads the F# modules. Both find the game types by folder or file, so a new game type is covered automatically.

The contract

GameTypeDefinition<Selection, Wire> in frontend/src/game-types/game-type-definition.ts. Selection is what the player configures, in book names from their own Bible. Wire is the game type's own case of the shared GameType, in book numbers.

MemberUsed by
name, hintStart screen, multiplayer tabs, play-request text
defaultSelectionWhether a game can start before anything is picked
renderSelectorSetup screen and challenge settings (each type owns its selector)
verseRestrictionSingleplayer: which verses to draw
guessConstraintSingleplayer: what the guess form offers
scoreGuessSingleplayer: how many points a guess earns (multiplayer: the backend module's scoreGuess)
toWireMultiplayer: the play request / matchmaking entry sent to the server
describeWireMultiplayer: the challenged player's description, in their own spelling
guessConstraintForWireMultiplayer: what the guess form offers, in the viewer's own spelling

The guess form is told what to offer through one explicit union, GuessConstraint (any-book / one-of-books / fixed-book), instead of separate optional properties. A combination that no game type produces can't be expressed at all.

Game rules

Every rule that decides how a game plays belongs to its game type, so each type's rules can be changed without touching the others:

  • Which verses — verseRestriction / backend restriction.
  • What can be guessed — guessConstraint / guessConstraintForWire.
  • Scoring — singleplayer scoreGuess in the frontend definition (the server never scores a singleplayer round), multiplayer scoreGuess in the backend module (the client never scores a multiplayer round).

The standard rules are building blocks in the shared kernel (frontend/src/shared-kernel/scoring.ts, backend/Domain/Scoring.fs). Each game type chooses one explicitly — The Bible and Books choose the standard ones, while Chapters has its own (what is given — the book, and a lone chapter — earns nothing — see Scoring). Replacing a rule means editing that game type's own file and its own test. Round count and time limit are still shared settings, not per-type rules.

Rules that span game types live in the registry

A game type with nothing picked yet plays as The Bible. For example, a challenge sent from the Books tab before any book is ticked is sent as AllVerses, and an empty Books is described as "The Bible". The registry owns that rule; no game type knows about another.

Adding a game type

  1. Create frontend/src/game-types/<name>/ with a definition implementing GameTypeDefinition, its selector component (if it has one) and its tests.
  2. Add a case to the wire type in frontend/src/shared-kernel/game-type-wire.ts and backend/Domain/GameTypes/GameType.fs. They are the same JSON contract and must change together.
  3. Register it in frontend/src/game-types/registry.ts (GameTypeId, SelectionById, WireById, DEFINITIONS, GAME_TYPE_IDS, definitionForWire). The compiler points out anything missed.
  4. Add backend/Domain/GameTypes/<Name>.fs with its restriction and scoreGuess, list it in BibleGuessr.Domain.fsproj before GameType.fs, dispatch to it from GameType.restrictionOf and GameType.scoreGuess, and add it to GameTypeScoringTests.fs.

The start screen, setup screen and multiplayer tabs then show the new game type without any changes.

Tests

Each game type has its own unit tests next to it (e.g. frontend/src/game-types/books/books.test.ts). The registry's cross-type rules are tested in frontend/src/game-types/registry.test.ts. The end-to-end behaviour is covered by the existing Playwright specs (book-selector.spec.ts, book-picker.spec.ts, play-request-accept-deny.spec.ts, the multiplayer specs).
