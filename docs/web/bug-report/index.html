Feature

Report a bug

An always-available way to report a technical problem, delivered to the application owner by email.

How it differs from the other two report flows

There are three, and they are deliberately kept apart. The Bible-file error reporter captures a filename and loader error automatically for a failed upload. Report abuse is about another player's behaviour. This one is for technical problems, and the spec is explicit that a bug must never be routed through the abuse endpoint.

Nothing is captured automatically here — no Bible file, verse text, chat history or game transcript. A report contains only what the player typed.

The panel

A bug button sits in the bottom-right corner, opposite the report-abuse control and clear of the nerd panel. It is a toggle: it opens the panel when closed and closes it when open, with the same semantics as Cancel, so nothing is submitted either way. Its accessible name and tooltip describe the action it will perform, and it exposes aria-expanded.

While a report is in flight the toggle is disabled, so a submission can never be interrupted or duplicated. Focus moves into the panel on open and returns to the button on close, and the screen underneath — game, room, chat, setup or results — is left untouched.

Delivery and privacy

Reports go to POST /api/bug-reports, its own contract. Every field is treated as untrusted input and HTML-encoded before it reaches the email body. The reporter's address is never the sender: the configured relay-authorised From stays, and their address is attached as Reply-To, with an unparseable one dropped rather than blocking delivery.

The endpoint shares the other report endpoints' per-IP and global rate limiters, since all three protect the same mail relay and a caller must not be able to dodge their budget by rotating between them. Validation runs before any mail is attempted, so malformed or oversized requests cost nothing and return 400; rate limits return 429; an SMTP failure returns 502, which the panel presents as retryable. Delivery failures are logged without report content or contact details.

Implementation

backend/Domain/GeneralBugReport.fs holds the type and a pure validate that trims, rejects empty descriptions and enforces lengths; backend/Api/MailSender.fs builds and sends the email; backend/Api/Program.fs exposes the endpoint. frontend/src/components/bug-report.ts owns the form and its submit-state model, and frontend/src/components/bg-app.ts owns the sticky toggle.

Validation is covered by backend/Tests/GeneralBugReportTests.fs; the panel, toggle, validation, duplicate-submit prevention, delivery failure, endpoint separation and state preservation by frontend/e2e/bug-report.spec.ts.
