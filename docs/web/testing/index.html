Testing

What's covered, what isn't, and exactly how to run all three layers.

Run everything

task dotnet:test        # backend unit tests (xUnit)
task frontend:test      # frontend unit tests (Vitest)
task frontend:test-e2e  # end-to-end tests (Playwright)

End-to-end tests need both dev servers already running in separate terminals (task dotnet:dev and task frontend:dev) — Playwright doesn't spawn either one itself, matching the repo's existing convention of running backend and frontend as two separate long-lived processes. Once per machine, install Playwright's browser binaries: cd frontend && npx playwright install.

Backend — xUnit

backend/Tests/BibleGuessr.Tests.fsproj

File Covers
ScoringTests.fs Scoring.pointsForVerseGuess — every gated tier, case-insensitivity.
RoomTests.fs addMessage truncation/ordering, play-request send/withdraw/accept/deny/filter functions.
PlayRequestTests.fs Retargeting (REPLACE), independent senders to the same target, isolated withdrawal.
DisconnectCleanupTests.fs Mark/reconnect/sweep semantics, and that a removal cleans up that player's play requests too.

All of these test pure functions in Game.fs directly — no SignalR mocking anywhere, by design (see the "pure domain function, thin hub wrapper" pattern mentioned on the play requests and player presence pages).

Frontend unit — Vitest

frontend/vitest.config.ts — node environment, since current targets are plain functions with no DOM dependency.

File Covers
local-verses.test.ts createLocalVerseSource's filtering, sorting, and dedup.
scoring.test.ts Same scenarios as the backend's ScoringTests.fs, for side-by-side comparison.
game-type.test.ts Building a GameType from a chosen scope/restriction, and describing one for display — see Start a game from chat.
Coverage gap

epub-parser.ts, rtf-parser.ts, and verse-cache.ts have no dedicated unit tests despite non-trivial parsing logic — see Bring your own Bible file.

End-to-end — Playwright

frontend/playwright.config.ts — every spec uses two independent browser contexts to simulate two separate players against the same live server.

File Covers
play-request.spec.ts Full send → receive → withdraw round trip.
play-request-accept-deny.spec.ts Send → receive (with the chosen game type shown) → accept, and send → receive → deny — the request clears on both sides either way.
player-presence.spec.ts Closing one context flips the other player's status dot live; a name survives a page reload. Does not drive the real 5-minute stale-removal sweep end-to-end — that would mean an actual 5-minute wait in CI — that path is covered by the backend unit tests instead.
