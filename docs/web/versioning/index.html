Procedure

Versioning

Where each version number lives, which ones derive from another and which are typed by hand, and what to edit when a feature is finished.

Two applications, two revisions

The frontend and the backend each carry their own revision, counted independently. They ship separately — the frontend as a zip on a GitHub release, the backend as a Docker image — so there is no attempt to keep the two numbers in step. A third number, the release version , names each release that ships them together.

CLAUDE.md states the rule: when a feature is complete, bump the version of each application it changed. A frontend-only change bumps only the frontend. A change touching both bumps both.

The frontend revision

frontend/package.json 's revision is the single source of truth — a plain integer, currently 1 , incremented by one whenever the frontend changes. It is not a semantic version, and it lives in its own field because npm reserves version for semver. Two things derive from it, and neither is edited by hand:

  • The meta tag users see. frontend/vite.config.ts reads package.json at build time and rewrites <meta name="application-revision"> in frontend/index.html through a transformIndexHtml plugin. The checked-in placeholder is 0 and never survives a build. frontend/src/components/nerd-panel.ts reads that tag to display the version in the Nerd panel.
  • The release zip filename — bibleguessr-frontend-r<revision>.zip .

The git tag does not derive from it — tags carry the release version instead.

To bump it, increment revision in package.json and rebuild. Nothing else needs touching.

Why the derivation exists

The meta tag used to be maintained by hand and drifted: package.json said 0.8.3 while the Nerd panel showed 0.7.2 , because nothing asserted the two agreed. Two checks now do — frontend/src/app-revision.test.ts against a fresh build, and build/fsx/VerifyFrontendArtifact.fsx against the artifact about to be packaged. See Frontend release for what that verification refuses to let through.

The backend revision

backend/Api/Program.fs holds it as an integer literal on line 46, the same kind of counter as the frontend's revision : 

let BackendRevision = 1

It is served from /api/revision , which the Nerd panel fetches and displays next to the frontend version. To bump it, increment the literal.

This is the weak spot

There is no <Version> property in backend/Api/BibleGuessr.Api.fsproj , so the backend revision has no build-time representation. Nothing outside the running process can read it the way the release scripts read package.json — a build script wanting the backend revision would have to parse F# source. The assemblies carry the .NET default 1.0.0.0 , unrelated to the literal.

This is a known gap, recorded under "The backend has no version" in docs/SCRUM/BACKLOG/Feature.CI-CD-construction.md .

The release version

One number names a release as a whole. It is used in three places, always identically:

  • The git tag — v<release version> , e.g. v0.0.1 . Pushing it triggers the release workflow.
  • The GitHub release , created from that tag.
  • The Docker image tag of both images, exported as IMAGE_TAG .

build/docker-compose.build.yml names both images after IMAGE_TAG , using the :? form so a missing value fails the build rather than producing an image tagged with an empty string: 

image: ${DOCKER_USERNAME:?}/bibleguessr-api:${IMAGE_TAG:?}
image: ${DOCKER_USERNAME:?}/bibleguessr-nginx:${IMAGE_TAG:?}

The release version is not an application revision. The two applications inside a release count their revisions separately, and a release records which of their revisions it contains through /api/revision and the Nerd panel.

Where the value comes from

Taskfile.yml and Taskfile.Docker.yml both obtain it through scripts/ci/load-image-version.sh : 

echo '0.0.1'

Its output is the whole mechanism: a hand-edited literal, the same way frontend/package.json 's version field is. Nothing derives it from a commit or either application version, and nothing is meant to — it is a third, independent value, edited as its own step in a release.

The tag and the script must agree

The release workflow's first job, check-tag , runs scripts/ci/check-release-tag.sh against the pushed tag and fails the run unless the tag is exactly v followed by what load-image-version.sh returns. Forgetting to bump the script therefore stops the release before anything is built or published, rather than overwriting the previous release's images. See Bumping a version for the full checklist a release goes through.

Getting it into a container build

There are two paths to docker compose , and they carry the variable differently.

Directly , via Taskfile.Docker.yml — task docker:build:app . Task exports IMAGE_TAG into the environment and docker compose interpolates it. Nothing else is involved.

DOCKER_USERNAME travels a different route: a gitignored root .env , passed with --env-file . In GitHub Actions it comes from the repository variable DOCKER_USERNAME instead. The Docker Hub token is the DOCKERHUB_ACCESSTOKEN_RW repository secret.

The release workflow is not run locally

.github/workflows/release.yml pushes both images to Docker Hub, so running it under act would overwrite the real release tag. It only runs on GitHub, from a pushed tag. CI is the check before a release; see Running the image build locally.

On a real GitHub runner

Both GitHub Actions workflows build through the same tasks as a local build (task docker:build:multi in CI, task docker:publish:app in a release), so they publish under whatever value the script currently returns, the same one a local build would produce from the same checkout. See Multi-platform images. No separate IMAGE_TAG workflow variable is necessary; the script is the single source, checked in like any other file.

Running the image build locally

To build both images for every published platform without pushing (the same task CI's docker-build job runs): 

task docker:build:multi

For a quick build for the host platform only, loaded into the local image store: 

task docker:build:app     # or docker:build:api / docker:build:nginx

task ci:act-ci runs ci.yml under act, which checks the workflow wiring. It never pushes. It is not a substitute for the buildx commands above, because docker-build needs backend-test, and that job fails under act on an arm64 host (actions/setup-dotnet fetches x64 binaries).

Two things that will bite

Running the chain under act can end in exitcode '137' — SIGKILL, the container being killed for running out of memory, usually while the .NET SDK unpacks or builds. It surfaces as a test failure but is not one; give Docker more memory.

scripts/ci/run-workflow.sh pipes through tee /dev/tty , which fails with No such device or address when there is no terminal — so the script cannot currently be run from a non-interactive context.

Bumping a version

The two revisions are incremented by a script rather than by hand, so only the number changes and a file it cannot parse is left untouched: 

task release:revision -- frontend          # or: backend, or: frontend backend

build/fsx/IncrementRevision.fsx checks every named target before writing any of them — if one file has no recognizable revision, or more than one, it exits non-zero and neither file is changed.

  • Frontend changed — increment revision in frontend/package.json .
  • Backend changed — increment BackendRevision in backend/Api/Program.fs .
  • Both changed — increment both, independently. They are counters, not meant to match.
  • Every release, regardless of what changed — edit the returned value in scripts/ci/load-image-version.sh to the new release version, and tag the release v followed by that value. This is not conditional on the frontend or backend bump above — every release needs its own number.

The release version is independent of the other two on purpose — it names the release, not either application. Its value does not need to match either bump above, only to be new and in n.n.n form.

Implementation

frontend/package.json holds the frontend revision; frontend/vite.config.ts injects it and frontend/src/app-revision.test.ts asserts it. backend/Api/Program.fs holds the backend revision and serves it at /api/revision .

scripts/ci/load-image-version.sh produces the release version, scripts/ci/check-release-tag.sh checks the pushed tag against it, Taskfile.yml and Taskfile.Docker.yml export it, Taskfile.CI.yml forwards it into act , and build/docker-compose.build.yml consumes it.

Frontend release covers how the frontend revision becomes a published artifact.
