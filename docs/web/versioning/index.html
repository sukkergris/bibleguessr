Versioning

Where each version number lives, which ones derive from another and which are typed by hand, and what to edit when a feature is finished.

Two applications, two version numbers

The frontend and the backend version independently. They ship separately — the frontend as a zip on a GitHub release, the backend as a Docker image — so there is no single "project version" and no attempt to keep the two numbers in step.

CLAUDE.md states the rule: when a feature is complete, bump the version of each application it changed. A frontend-only change bumps only the frontend. A change touching both bumps both.

The frontend version

frontend/package.json is the single source of truth. It currently reads 0.8.3 . Three things derive from it, and none of them is edited by hand:

  • The meta tag users see. frontend/vite.config.ts reads package.json at build time and rewrites <meta name="application-version"> in frontend/index.html through a transformIndexHtml plugin. The checked-in placeholder is 0.0.0 and never survives a build. frontend/src/components/nerd-panel.ts reads that tag to display the version in the Nerd panel.
  • The release zip filename — bibleguessr-frontend-<version>.zip .
  • The git tag — frontend-v<version> .

To bump it, edit package.json and rebuild. Nothing else needs touching.

Why the derivation exists

The meta tag used to be maintained by hand and drifted: package.json said 0.8.3 while the Nerd panel showed 0.7.2 , because nothing asserted the two agreed. Two checks now do — frontend/src/app-version.test.ts against a fresh build, and build/fsx/VerifyFrontendArtifact.fsx against the artifact about to be packaged. See Frontend release for what that verification refuses to let through.

The backend version

backend/Api/Program.fs holds it as a literal on line 46: 

let BackendVersion = "0.5.3"

It is served from /api/version , which the Nerd panel fetches and displays next to the frontend version. To bump it, edit the literal.

This is the weak spot

There is no <Version> property in backend/Api/BibleGuessr.Api.fsproj , so the backend version has no build-time representation. Nothing outside the running process can read it the way the release scripts read package.json — a build script wanting the backend version would have to parse F# source. The assemblies carry the .NET default 1.0.0.0 , unrelated to the literal.

This is a known gap, recorded under "The backend has no version" in docs/SCRUM/BACKLOG/Feature.CI-CD-construction.md .

The container image tag

build/docker-compose.build.yml names both images after an environment variable, using the :? form so a missing value fails the build rather than producing an image tagged with an empty string: 

image: ${DOCKER_USERNAME:?}/bibleguessr-api:${IMAGE_TAG:?}
image: ${DOCKER_USERNAME:?}/bibleguessr-nginx:${IMAGE_TAG:?}

IMAGE_TAG is a deployment coordinate, not an application version. It tags both images together, while the two applications inside them version separately.

Where the value comes from

Taskfile.yml and Taskfile.Docker.yml both declare it as a dynamic root-level env: entry: 

env:
  IMAGE_TAG:
    sh: ./scripts/ci/load-image-version.sh

Task runs that script once and exports the result to every task, including included taskfiles. That is why ${IMAGE_TAG} resolves inside a task that does not declare it itself — a per-task env: block repeating IMAGE_TAG: '{{.IMAGE_TAG}}' is redundant.

load-image-version.sh is a stub

It is three lines and echoes a hardcoded 0.0.1 . Every image built today carries that tag regardless of what either application's version says. Making the tag meaningful means giving this script a real source; until then, treat published tags as not identifying a build.

Getting it into a container build

There are two paths to docker compose , and they carry the variable differently.

Directly , via Taskfile.Docker.yml — task docker:build:app . Task exports IMAGE_TAG into the environment and docker compose interpolates it. Nothing else is involved.

Through the CI workflow under act , via Taskfile.CI.yml . Here the value has to cross into a container, which needs an explicit flag: 

./scripts/ci/run-ci-workflow.sh --env-file .env -j docker-build --env IMAGE_TAG="${IMAGE_TAG}"

--env sets a real environment variable in the job's shell, and works even though .github/workflows/ci.yml does not declare IMAGE_TAG in its env: block.

--env , not -s

-s passes a secret , reachable only as ${{ secrets.IMAGE_TAG }} inside the workflow YAML. It is never exported to the job's shell, so docker compose sees nothing and the build fails with required variable IMAGE_TAG is missing a value . The two flags look interchangeable and are not.

DOCKER_USERNAME travels a different route: a gitignored root .env , passed with --env-file . In GitHub Actions it comes from the DOCKERHUB_USERNAME secret instead.

On a real GitHub runner

There is no --env flag on GitHub Actions, so IMAGE_TAG must be declared in the workflow. The docker-build job in .github/workflows/ci.yml currently sets only DOCKER_USERNAME and COMMIT_SHA , so a pushed run will fail the same way the local run did until an IMAGE_TAG entry is added there.

Running the image build locally

To exercise only the container build, go straight at it: 

task docker:build:app     # or docker:build:api / docker:build:nginx

task ci:act-build-images looks like the equivalent but is not. -j docker-build does not run that job alone — docker-build declares needs: [backend-test, frontend-test] , and act honours it, so the whole test suite runs first. Use it to rehearse the full CI chain, not to check an image build.

Two things that will bite

Running the full chain locally can end in exitcode '137' — SIGKILL, the container being killed for running out of memory, usually while the .NET SDK unpacks or builds. It surfaces as a test failure but is not one; give Docker more memory.

scripts/ci/run-ci-workflow.sh pipes through tee /dev/tty , which fails with No such device or address when there is no terminal — so the script cannot currently be run from a non-interactive context.

Bumping a version

  • Frontend changed — edit version in frontend/package.json .
  • Backend changed — edit BackendVersion in backend/Api/Program.fs .
  • Both changed — edit both, independently. They are not meant to match.

Neither bump affects the image tag today, since load-image-version.sh ignores both.

Implementation

frontend/package.json holds the frontend version; frontend/vite.config.ts injects it and frontend/src/app-version.test.ts asserts it. backend/Api/Program.fs holds the backend version and serves it at /api/version .

scripts/ci/load-image-version.sh produces the image tag, Taskfile.yml and Taskfile.Docker.yml export it, Taskfile.CI.yml forwards it into act , and build/docker-compose.build.yml consumes it.

Frontend release covers how the frontend version becomes a published artifact.
