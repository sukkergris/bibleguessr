Infrastructure

Request routing

How the browser reaches the API and the SignalR hub over HTTPS on bibleguessr.single — everything same-origin, and why that removed CORS rather than reconfiguring it.

One origin, three kinds of request

The browser only ever talks to a single origin: https://bibleguessr.single. The web server in front decides what each path belongs to, and the frontend never names a backend host of its own.

  • /api/… — the REST API, proxied to the backend.
  • /hubs/… — the SignalR hub, proxied to the same backend as a WebSocket.
  • everything else — the frontend (the Vite dev server in the replica).

Because the page, the API and the hub share a scheme, host and port, these are same-origin requests. That is the whole reason the CORS configuration could be deleted rather than updated — see No CORS below.

Two front ends, same shape

There are two ways to run the app, and both present the same origin layout so that code written against one works against the other unchanged:

  • The server replica — nginx terminates TLS on bibleguessr.single and proxies /api/ and /hubs/ to the backend, with / going to the frontend.
  • Plain vite dev on :5173 — Vite's own dev proxy forwards the same two prefixes to the backend. Without this, the dev server would answer /hubs/game itself and the hub would never reach the backend at all.

The API prefix is real, not stripped

Every backend route is declared with its /api/ prefix already on it — /api/version, /api/verses/random, /api/rooms, and so on. The proxy therefore passes the path through unchanged.

An earlier rewrite ^/api/(.*)$ /$1 break; in the nginx location stripped the prefix before forwarding, which meant the backend was asked for /version — a path it does not serve. Removing the rewrite is what makes the prefix line up on both sides. If a route ever stops resolving through nginx but works when the backend is called directly, this is the first thing to check.

The hub needs its own location

/hubs/ is matched before the catch-all /, because the hub lives on the backend and the catch-all points at the frontend. Two details in that block are load-bearing:

  • WebSocket headers. The block includes the WebSocket proxy params, which forward Upgrade and Connection. The ordinary proxy params do not, and without them the upgrade handshake never completes — the request simply hangs instead of returning an error, which is what makes this failure mode confusing to diagnose.
  • Long read/send timeouts. A hub connection stays open with no traffic between rounds. The default 60-second read timeout would drop an idle connection and force a visible reconnect mid-game.

Rate limiting is deliberately not applied here. A hub connection is one long-lived request rather than many short ones, so the API's per-request limit does not describe it usefully.

Why the client only speaks WebSockets

The client pins the WebSockets transport and sets skipNegotiation, so there is no HTTP "negotiate" round-trip and no fallback to Server-Sent Events or long polling. The practical consequence for routing is that /hubs/game is only ever seen as an upgrade request — a proxy that handles plain HTTP correctly but drops the upgrade headers will fail every time, not intermittently.

Over TLS the client derives wss:// from the page's own origin, so the hub inherits the certificate and the host without being told about either.

No CORS

The backend configures no CORS policy at all, and this is intentional rather than an omission. Same-origin requests are not subject to CORS, so a policy would grant nothing; what it would do is introduce a second place where the frontend's origin is written down, free to drift from the real one. The previous setup had exactly that shape: an allowed origin defaulting to http://localhost:5173, which stopped describing reality the moment the app moved to HTTPS on bibleguessr.single.

If the frontend is ever served from a genuinely different origin, CORS has to come back — but it should come back deliberately, as a decision about that deployment, not as configuration carried forward by habit.

Verifying a change here

Routing failures are easy to mistake for application bugs, so check the layers separately. A WebSocket handshake that works is a 101 Switching Protocols:

  • Backend directly on its own port — proves the hub itself is up.
  • Through nginx over TLS with the real Host — proves the proxy block.
  • Through Vite on :5173 — proves the dev-server path.

An empty response rather than an HTTP error status is the signature of upgrade headers being dropped. Note that a missing /hubs/ block in nginx can be masked by the catch-all forwarding to Vite, which may then proxy to the backend itself — so when testing whether a given layer is doing the work, remove one layer at a time rather than trusting a single end-to-end success.

Implementation

server-replica/nginx/conf.d/10-bibleguessr.conf holds the /api/ and /hubs/ locations and the upstream definitions. server-replica/nginx/includes/proxy-websocket.conf carries the upgrade headers. frontend/vite.config.ts mirrors the same routing for plain vite dev.

frontend/src/api.ts holds the empty base URL that makes API calls same-origin, and frontend/src/signalr-client.ts builds the hub URL from it. backend/Api/Program.fs declares the /api/-prefixed routes and maps the hub at /hubs/game.
