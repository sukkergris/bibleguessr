Feature

Multiplayer round sync

What happens after a play request is accepted: a server-authoritative GameSession that picks each round's verse, times it, scores both players' guesses, advances or ends the game, and hands both players a final scoreboard — while verse text never once crosses the wire.

Builds on Multiplayer rooms & chat (the hub/room foundation) and Start a game from chat (how a game gets proposed and accepted in the first place — this page picks up exactly where accepting leaves off).

What it does, end to end

  1. A challenger picks a game type, round count, and time limit (<bg-challenge-settings>) and sends a play request — see Start a game from chat.
  2. The challenged player accepts. The server picks a first verse reference (never its text), starts a GameSession, and broadcasts RoundStarted to the room — both players land on the same round, at the same moment, seeing the same reference.
  3. Each client independently resolves that reference into displayable text from its own chosen translation/file, then shows <bg-verse-card> + <bg-guess-form> (reused verbatim from singleplayer).
  4. Each player submits a guess. Once both have guessed — or the round's time limit elapses, whichever comes first — the server scores the round, broadcasts RoundScored, and either starts the next round (RoundStarted again) or ends the game (GameOver).
  5. On GameOver, both clients tear down the round view and show <bg-multiplayer-results> — a final scoreboard with a per-round breakdown assembled entirely client-side.

Domain model

backend/Domain/Game.fs

type TimeLimit =
    | Unlimited
    | LimitedTo of TimeSpan

type GameSession =
    { PlayerA: PlayerId
      PlayerB: PlayerId
      GameType: GameType
      RoundCount: int
      RoundTimeLimit: TimeLimit
      RoundIndex: int
      Round: RoundState
      RoundStartedAt: DateTimeOffset option
      GuessesThisRound: Map<PlayerId, Guess>
      Scores: Map<PlayerId, int> }

type GameOverReason =
    | Completed
    | Forfeited of remainingPlayer: PlayerId option

TimeLimit is a named DU rather than a bare TimeSpan option so "no limit" is a case every consumer (scoring, the timeout sweep) has to handle explicitly, instead of an ambiguous None that could be misread as "not set yet." The time-per-verse slider in <bg-challenge-settings> runs 0–60 seconds, where 0 means Unlimited.

A GameSession lives at Room.ActiveGame: GameSession option — at most one per room at a time, and each player may be in at most one active game across the whole app (enforced at SendPlayRequest/AcceptPlayRequest, not in the domain itself — see the concurrency section below). RoundIndex is 0-based; GuessesThisRound is cleared on every advanceRound; Scores is a running total across the whole game, seeded to 0 for both players at start — deliberately not Player.Score, which stays unused, since a game's score belongs to the game, not a player record that outlives many games in the same room.

GameOverReason distinguishes a normally-completed game from a forfeited one. Forfeited carries the surviving player, if there is one — both players can be gone at once (a simultaneous disconnect sweep), in which case it's None and neither side is declared a winner.

The GameSession module (start, submitGuess, bothGuessed, scoreRound, advanceRound, isOver, isRoundExpired) is pure — every timestamp it needs (startedAt, scoredAt, now) is passed in rather than read from DateTimeOffset.UtcNow internally, which is what makes all of it unit-testable without any SignalR or background-service plumbing (see backend/Tests/GameSessionTests.fs).

Verse text never crosses the wire

Per CLAUDE.md's data-security rule, uploaded verse text must never be sent to the server or to other players — only book/chapter/verse numbers may be transmitted. A multiplayer round's server-side state reflects this directly: 

type VerseReference =
    { Book: string
      BookNumber: int
      Chapter: int
      VerseNumber: int }

type RoundState =
    | WaitingForPlayers
    | InProgress of VerseReference
    | Scored of VerseReference * GuessResult list

RoundState only ever carries a VerseReference, never a full Verse — there is no field anywhere in a GameSession that could hold verse text. The server picks which verse a round is about and scores guesses against it purely from these fields. Each client independently resolves the reference to displayable text from its own locally-chosen VerseSource — the server never renders or forwards anyone's text, and two players in the same game may legitimately be reading two different translations or uploaded files for the very same round.

Book is kept on VerseReference purely for display (it's whichever pool's spelling picked the round's verse, typically the server's own) — matching/scoring always goes through BookNumber, never Book.

Frontend resolution — frontend/src/local-verses.ts / frontend/src/api.ts

VerseSource.lookupVerse(reference, translation) is the one call every client makes to turn a bare reference into something displayable, always against the viewer's own chosen translation/file — never the opponent's, never anything the server pushes. For the server-backed source (frontend/src/api.ts), this hits GET /api/verses/lookup, which prefers bookNumber over the reference's book name for exactly the reason above — matching by name would reintroduce the cross-translation spelling mismatch bookNumber exists to fix. For an uploaded file (frontend/src/local-verses.ts's createLocalVerseSource), the same resolution happens entirely client-side against the parsed Verse[] in memory — no network call at all, so an uploaded file's text never leaves the browser it was parsed in.

If a player's own source can't find the referenced verse at all (a real translation/file mismatch — see the book-number section below for why this is rare but possible), <bg-multiplayer-game> shows a small error in place of the verse card for that round rather than a broken guess form — the round still resolves normally via the opponent's guess or the timer even for the player who can't see it.

The book-number matching system

backend/Domain/Verses.fs (Verse.bookNumbers, bookNumberOf, bookAtNumber, matchesRestrictionByNumber)

Since verse text can never cross the wire, and two players may have entirely different Bible files/translations, something else has to let them agree on "which book" a guess or restriction refers to. Book names can't be trusted for this — not just across translations/languages (a challenger's Danish file might call a book "1.Mosebog" while the server's own pool calls it "Genesis"), but even within the very same translation: a real production bug in the bibelen-dk loader produced both "Jeremias" and "Jeremias." (trailing period) for what is really one book, a parsing artifact that shifted every later book's number by one and once caused a round to reference an impossible verse ("Markus 25:38" — the real Markus/Mark has only 16 chapters). See backend/Tests/BibelenDkLoaderTests.fs for the fix (normalizeBookNames) and backend/Tests/BookNumberTests.fs for the matching fix itself.

The fix: every book gets a stable number instead of being identified by name — its 1-based position in the order it's first encountered in a verse list. This is exactly the "Bible order" (Genesis..Revelation) every loader already produces by construction, just finally captured as a number. Two different sources that agree on every earlier book's presence/order will assign the very same book the very same number, regardless of how each one spells it — "Dommer" in one file and "Dommerne" in another both land on book 7 if both files agree on the six books before it.

This number is what actually crosses the client/server boundary, in three places:

  • GameType.Books/Chapters — a challenger restricts a game to books/chapters picked from their own source, so what's sent is the book numbers their own source assigned, not names.
  • VerseReference.BookNumber — the round's verse, numbered against the server's own pool (the reference edition everything is ultimately matched against).
  • Guess.BookNumber — a submitted guess, numbered against the guessing player's own source (see frontend/src/game-type.ts's bookNumberOfGuess and frontend/src/book-numbers.ts).

Scoring.isCorrectGuess (backend) matches a guess to the round's verse by BookNumber whenever the guess has one, falling back to name matching only if the guessing player's own source couldn't resolve a number for what they typed at all (e.g. free-text entry the source doesn't recognize). See backend/Tests/MultiplayerScoringByNumberTests.fs and backend/Tests/GameTypeNumberTests.fs for the full matrix.

Known limit

Two sources only agree on a book's number as long as they agree on every earlier book's presence/order too — a file missing a book, or covering a different canon, disagrees with another from that point on. Accepted the same way this codebase already accepts that per-player translation/file mismatches are rare, rather than solved outright.

Hub protocol

backend/Api/GameHub.fs

Method / Event Direction Payload
AcceptPlayRequest(fromPlayerId) client → server the challenger's PlayerId string. On success, picks the first verse and starts the GameSession — see below.
SubmitGuess(book, bookNumber, chapter, verseNumber) client → server the caller's guess for the current round of their active game. bookNumber is optional (None if the caller's own source couldn't resolve one). No broadcast on an individual submission — the round only announces itself once resolved.
ForfeitGame() client → server — (no-op if the caller has no active game)
RoundStarted server → room group the full GameSession — sent right after AcceptPlayRequest succeeds (round 0) and again every time a round advances. A full snapshot, not a delta, so a client that remounts mid-game always has authoritative state.
RoundScored server → room group the full GameSession, with Round now the Scored case
GameOver server → room group (Scores, PlayerA, PlayerB, Reason) — Scores is the full final running total per player id, Reason is a GameOverReason
Error server → caller only a plain error message string (e.g. "You don't have an active game", "This round is no longer accepting guesses")

Every game event is broadcast to the whole room group, not routed to just the two players involved — the same tradeoff play requests already make, since RoomStore has no PlayerId → connectionId reverse index. A room can have more than one game running concurrently (e.g. two unrelated pairs in World chat), so <bg-multiplayer-game> filters every event to sessions/scores that actually name its own two players before acting on them.

How a round resolves — resolveRound

Scoring a round, broadcasting the result, and deciding whether to advance or end the game is shared logic — GameHub.fs's private resolveRound function — called from two different places that both need to do exactly the same thing:

  • SubmitGuess, the instant both players have a guess recorded for the current round.
  • RoundTimeoutService's sweep, the instant a round's time limit elapses (see below).

resolveRound scores the round (GameSession.scoreRound) and decides whether to end the game or advance to a freshly-picked verse entirely inside one RoomStore.Update call (see the concurrency callout below) — not against a session snapshot the caller already had lying around — then broadcasts RoundScored and either GameOver(Completed) (last round) or RoundStarted again. A player who never guessed the round gets no GuessResult entry at all — an implicit 0, distinguishable from "guessed wrong."

Fixed during this feature: a real lost-write race in RoomStore

Every hub method that touches a room — SubmitGuess included — used to do a plain TryGet room -> compute newRoom -> Set(code, newRoom) sequence. Each step is atomic on its own (ConcurrentDictionary), but the sequence as a whole isn't: two players submitting a guess for the same round at nearly the same instant could each TryGet the same starting snapshot, compute two different updates from it, and then Set one after the other — the second Set silently discarding the first caller's entire change. This could lose a guess outright (the round never resolves, since bothGuessed never becomes true for either caller) or resurrect an already-ended ActiveGame, permanently stuck-blocking that room's players ("You can't send a play request while a game is in progress" with no game visibly running, even after a real game had already finished).

The fix: RoomStore.Update(code, f: Room -> Room) — a real optimistic compare-and-swap retry loop (TryGetValue + TryUpdate, retried on contention) — replaces every TryGet+Set pair across the whole hub, not just in resolveRound/SubmitGuess. RoomStore.Set itself was removed once nothing called it anymore, so the footgun can't be reached by a future call site. See backend/Tests/RoomStoreConcurrencyTests.fs — including a test that reintroduces the old pattern and confirms it fails these tests reliably.

Timer & timeout sweep

A round's countdown is computed entirely client-side, from RoundStartedAt + RoundTimeLimit (see frontend/src/timer.ts's deadlineOf/computeRemainingSeconds) — no server round-trip needed just to tick a clock down. But something server-side still has to actually enforce the deadline once it passes, even if a player never submits anything.

backend/Api/GameHub.fs's RoundTimeoutService is a BackgroundService that sweeps every room's ActiveGame once a second, looking for a round whose GameSession.isRoundExpired is true, and calling the exact same resolveRound function SubmitGuess uses.

Why a sweep instead of a scheduled per-round callback

A per-round Task.Delay/timer callback would need to be cancelled the instant SubmitGuess resolves the same round early (both players guessed before time ran out) — that's real cancellation-token plumbing threaded through every round-advance path, and a real race if the callback fires at the same moment a guess lands. A periodic sweep sidesteps all of it: GameSession.isRoundExpired only ever matches a round that's still InProgress, so a round SubmitGuess already advanced or scored a moment earlier is simply skipped on the sweep's next tick. Self-healing against races, no cancellation or locking needed — consistent with RoomStore.Update's own atomic read-modify-write (see the callout above). The 1-second interval (vs. PlayerCleanupService's 30s — see Player presence) keeps a short round timer feeling responsive, while still being trivially cheap for what's normally a handful of in-memory rooms.

Forfeit — two paths, one shape

A game can end early two ways, and both funnel through the exact same GameOver(Forfeited remainingPlayer) broadcast shape:

  • Explicit — ForfeitGame(). The caller clicks Forfeit in <bg-multiplayer-game>, confirms a browser confirm() dialog, and the hub method ends the game (Room.forfeitGame) and broadcasts GameOver naming the opponent as the surviving player.
  • Implicit — disconnect past the grace period. If a participant in an active game disconnects and stays gone longer than Room.disconnectGracePeriod (5 minutes — see Player presence), PlayerCleanupService's periodic sweep removes them and, because Room.removeStaleDisconnections also ends any ActiveGame they were part of, broadcasts GameOver(Forfeited) naming whoever's left.

Both players being gone at once (a simultaneous disconnect sweep, or a room-cleanup edge case) yields Forfeited None — no winner declared. On the frontend, <bg-multiplayer-results>'s headline handles this explicitly ("Game ended" rather than guessing a winner).

One active game per player

A GameSession lives on Room, but the domain layer itself doesn't stop the same player from somehow ending up in two sessions across two different rooms — that guard is enforced at the hub layer, in backend/Api/GameHub.fs:

  • SendPlayRequest refuses (Error, no request created) if either the sender or the target is already in an active game (Room.isInActiveGame).
  • AcceptPlayRequest refuses the same way, as a last-moment re-check — closing the (small) race where either player joined a different game between sending/receiving the request and accepting it.

See backend/Tests/RoomActiveGameTests.fs for the pure-domain side of this (Room.isInActiveGame, startGame, updateGame, endGame, forfeitGame).

Frontend component tree

<bg-challenge-settings> (frontend/src/components/challenge-settings.ts) wraps the existing <bg-game-type-select> and adds two sliders — round count (3–10) and time limit (0–60s, 0 meaning unlimited) — firing challenge-settings-changed. It sits above the players list exactly where the game-type selector used to sit on its own.

Once a game is active, frontend/src/components/bg-room-setup.ts swaps the whole game-type-select/chat/play-requests block out for <bg-multiplayer-game> (frontend/src/components/multiplayer-game.ts) — the stateful orchestrator for everything moment-to-moment: the current round's resolved verse, my own "guess locked in" state, the client-side countdown, the opponent's live connection status, and the running scoreboard. It reuses <bg-verse-card>/<bg-guess-form> verbatim from singleplayer — no multiplayer-specific fork of either — and fires game-over (server said the game ended) or game-ended (a purely local teardown, e.g. the opponent left the room entirely) back up to bg-room-setup.ts.

Fixed: the game's first round could be silently lost on mount

AcceptPlayRequest broadcasts PlayRequestAccepted then RoundStarted in quick succession. PlayRequestAccepted's handler in bg-room-setup.ts is what mounts <bg-multiplayer-game> for the very first time — and that component's own onRoundStarted subscription only started in its connectedCallback, which by definition runs strictly after that mount. SignalR's hub.on has no replay/buffering for a listener that subscribes late, so if RoundStarted happened to land in the gap between the two broadcasts and the new component's connectedCallback actually running, the game's very first round was lost outright — the player got stuck on "Waiting for the first verse…" forever (an Unlimited-time-limit game never recovered at all; a timed one eventually self-healed once RoundTimeoutService's sweep caught the "expired" round and re-sent a fresh RoundStarted).

Fixed by moving the catch: bg-room-setup.ts (already mounted for the whole room's lifetime, well before any of this happens) now also subscribes to onRoundStarted directly, alongside its other long-lived subscriptions, capturing whatever session it last saw into an initialSession field. That's passed to <bg-multiplayer-game> as an initialSession property, applied in connectedCallback (via a shared _applyRoundStarted helper) before the child's own subscription starts — closing the race structurally instead of depending on subscribe-before-broadcast timing luck. Verified via multiplayer-round.spec.ts --repeat-each=6: 42/42 passed with zero flakes, versus a previously-reproducible ~30-50% failure rate under the same conditions.

On game-over, bg-room-setup.ts shows <bg-multiplayer-results> (frontend/src/components/multiplayer-results.ts) — the final scoreboard plus a per-round breakdown. That breakdown is accumulated entirely client-side, one entry per RoundScored event <bg-multiplayer-game> receives — the server itself keeps no round history beyond the current round's GuessesThisRound. A "Back to room" button clears both mpResults and activeGameOpponent in bg-room-setup.ts, returning to the normal room view.

Because GameType/Guess carry book numbers, not names, several pieces of UI have to resolve a number back to this viewer's own spelling before displaying or restricting anything — see frontend/src/game-type.ts's allowedBooksForGuessForm, lockedBookForGuessForm, allowedChaptersForGuessForm, and bookNumberOfGuess (used when submitting a guess), all of which are async since resolving a number needs an awaited getBooksInBibleOrder() call against the viewer's own VerseSource.
