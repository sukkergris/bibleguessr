Feature

Bible data volume

The API image ships the public-domain bibelen-dk archive and unpacks it into a data folder on startup (a Docker volume in production, a gitignored folder in development) before loading verses from there.

Why this exists

The published API image used to contain no Bible data. The API started, logged Verses loaded: 0, answered /api/translations with [], and still reported itself healthy. The Danish 1931/1907 translation is public domain (see NOTICE.md), so the image now carries it. Unpacking it into a volume lets operators inspect the files on the server.

Image layout

Path in the image What it is
/app/bibles/bibelen-dk/src/Bibelen Files.zip The shipped archive, copied as a single file. build/Dockerfile.api never copies bibles/ as a whole, and .dockerignore excludes jw.org paths as a second guard.
/data/bibles The data directory, declared as a VOLUME and owned by the non-root apiuser.
/data/bibles/bibelen-dk/ The unpacked chapter pages the API loads verses from.

Configuration

Key Image default (ENV) dotnet run default
Verses:ArchivePath /app/bibles/bibelen-dk/src/Bibelen Files.zip ../../bibles/bibelen-dk/src/Bibelen Files.zip
Verses:DataDirectory /data/bibles ../../bibles/.data (gitignored)

As environment variables, use a double underscore: Verses__ArchivePath, Verses__DataDirectory. The image works without setting either. The old Verses:Directory key is no longer read.

What happens on startup

backend/Api/BibleArchiveUnpacker.fs runs before verses are loaded. It compares the archive's SHA-256 with a marker file, .archive.sha256, inside the unpacked folder:

Unpacked folder Action Log line
Missing Unpack Unpacked Bible archive … (reason: first run …)
Present, no marker Unpack, replacing the contents … (reason: the folder has no marker …)
Marker matches the archive Nothing Bible archive already unpacked …; skipping unpack
Marker names a different archive (for example, after an image upgrade) Unpack, replacing the contents … (reason: archive changed from sha256 … to …)
  • Atomic. Extraction goes to .bibelen-dk.tmp-<id> next to the target, and the marker is written into it once extraction completes. Only then is the temp folder renamed into place. The previous folder is moved aside to .bibelen-dk.old-<id> during the swap. Leftover temp and old folders from a crash are deleted on the next start, and a missing target is unpacked again. The data directory itself is never renamed, because it may be a mount point.
  • Zip-slip safe. An entry whose path resolves outside the temp folder (such as ../evil.html) rejects the whole archive, and nothing is written.
  • Never fatal. A missing archive logs a warning and loads whatever is already unpacked. A failed unpack logs an error.

Health when no verses load

If no verses load, the API logs an error, and /api/healthz (and /api/health) answer 503 with {"status":"unhealthy","versesLoaded":0}, so an empty game never looks healthy. The connection panel shows this as an error.

Production setup

The production compose file and webapi.env live on the server, outside this repository. Apply these edits there: 

# bibelguessr-server/docker-compose.yml
services:
  api:                       # the bibleguessr-api service
    volumes:
      - bible-data:/data/bibles

volumes:
  bible-data:

Remove Verses__Directory from webapi.env: the image's defaults are correct, and the key is no longer read.

Bind mounts

A fresh named volume inherits apiuser's ownership of /data/bibles from the image. A bind mount does not: the host folder must be writable by the container user's UID (check it with docker run --rm --entrypoint id bibleguessr-api), or the unpack fails and health reports 503.

Tests

backend/Tests/BibleArchiveUnpackerTests.fs covers the unpack decision, first run, restart, changed archive, interrupted unpack, and zip-slip. It also checks that the real archive, once unpacked, loads exactly the same verses in the same order as reading the zip. Order matters because book numbers come from first-encounter order.
