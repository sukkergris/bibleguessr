Feature

Multiplayer rooms & chat

Room codes, the always-open World chat, and the SignalR hub protocol that the play-request and presence features both build on top of.

What it does

A player either creates a room (gets a random 4-digit code to share) or joins World chat — an always-open room anyone can join with just a name, no code. Once in, everyone sees a live players list and a real-time text chat. Round/scoring sync is now fully built on top of this foundation — see Multiplayer round sync for the synced-gameplay layer (verse picking, guessing, scoring, timers, forfeit, results) — this page just covers the room and chat foundation it's built on.

Backend

The Room type

backend/Domain/Game.fs

type Room =
    { Code: RoomCode
      Players: Player list
      Round: RoundState
      RecentMessages: ChatMessage list
      PendingRequests: PlayRequest list
      DisconnectedPlayers: Map<PlayerId, DateTimeOffset>
      ActiveGame: GameSession option }

RecentMessages is capped at Room.maxRecentMessages = 20, newest first, trimmed on every Room.addMessage call — enough for a new joiner to land in a chat with context, without keeping unbounded history for a long-lived room. PendingRequests, DisconnectedPlayers, and ActiveGame belong to the play-request, presence, and round-sync features respectively — see their own pages.

RoomStore

backend/Api/GameHub.fs — registered as a singleton in Program.fs

Two ConcurrentDictionarys: rooms (room code → Room) and connections (SignalR connection id → RoomCode * Player). The second one exists so a later hub call on the same connection (e.g. sending a chat message) can identify its sender from the connection itself, rather than trusting whatever identity the client claims in the call's arguments.

Known limitation

Everything is in-memory, single-instance. Fine for a hobby deployment; scaling out to multiple server instances would need a distributed store (e.g. a Redis backplane) behind the same interface.

Creating vs. joining

Room creation is a plain REST endpoint, not a hub method — POST /api/rooms calls rooms.CreateRoom() (random 4-digit code) and returns the Room. Everything else — joining, chatting, play requests, presence — goes through the SignalR hub at /hubs/game.

World chat reuses the exact same join path with a reserved, non-numeric room code (WorldChatRoomCode = "WORLD", so it can never collide with a generated 4-digit code), created lazily on first use via RoomStore.GetOrCreateWorldRoom().

Hub methods

Method What it does
JoinRoom(roomCode, playerName) Joins an existing room by code. Sends "Error" and throws if the code doesn't exist.
JoinWorldChat(playerName) Joins (creating if needed) the World chat room.
SendChatMessage(text) Trims the text; rejects empty or over maxChatMessageLength = 500 chars via "Error"; otherwise records it into RecentMessages and broadcasts it.

Both join methods return Task<Player> — the caller's newly-minted Player (fresh PlayerId every time). The frontend needs this to know which entry in its own players list is "me".

What joining actually does

Both join methods delegate to a shared private JoinExistingRoom(room, playerName):

  1. Mints a new Player { Id = Guid.NewGuid(); Name; Score = 0 } and prepends it to the room.
  2. Registers the connection → (room, player) mapping in RoomStore.
  3. Adds the SignalR connection to a Group named by the room code.
  4. Broadcasts PlayerJoined to the group (payload: the new Player).
  5. Sends the caller (only) ChatHistory — recent messages, oldest first.
  6. Sends the caller (only) RoomPlayers — the full roster, including themself.

The RoomPlayers snapshot exists specifically so a joiner sees everyone who was already there — without it, they'd only ever learn about players who join after them via future PlayerJoined broadcasts.

Events

Event Sent to Payload
PlayerJoined room group the new Player
ChatMessageReceived room group ChatMessage
ChatHistory caller only, once on join ChatMessage[], oldest first
RoomPlayers caller only, once on join Player[], full snapshot incl. self
Error caller only a plain error message string

RoundStarted and RoundScored are also declared (and mirrored in the frontend's HubEvents) and are now fully wired — sent from AcceptPlayRequest, SubmitGuess, and the round-timeout sweep, and consumed by <bg-multiplayer-game>. See Multiplayer round sync for the full protocol and how a round actually resolves.

Frontend

frontend/src/signalr-client.ts wraps the raw SignalR connection: one export async function verbNoun(...) per hub method (e.g. joinRoom, sendChatMessage) and one export function onXyz(handler): () => void per event, each returning an unsubscribe function. A HubEvents constant mirrors the backend's event literal strings by hand, with a comment flagging that they must be kept in sync.

frontend/src/components/bg-room-setup.ts is the "smart" component that owns all of this state — the create/join/World-chat screen, the joined players list, chat messages, and (once those features exist) play requests and presence. It renders frontend/src/components/chat-panel.ts, a "dumb" reusable view that just takes players/messages in as properties and fires plain CustomEvents out (chat-submit, player-selected).

Connection race, already handled

getGameHubConnection() caches the in-flight start promise, not just the connection object — the object is truthy the instant HubConnectionBuilder().build() returns, well before .start() resolves. Several call sites invoke it back-to-back on the same tick, so caching only the object let an early caller invoke on a connection that wasn't Connected yet. Caching the promise means every caller awaits the same in-flight start.

Round sync

Now built

A synced, server-authoritative multiplayer round loop — verse picking, guessing, scoring, round advancement, a timer with a background timeout sweep, forfeit, and a final results screen — is fully built on top of the room/chat foundation documented on this page. It lives on GameSession, nested inside Room.ActiveGame (see below), not on the legacy Room.Round field. See Multiplayer round sync for the full write-up.

Note: Room.Round: RoundState is still present on the Room type shown above, but it is superseded — never read or transitioned by any hub code path. The real round state for an active game is GameSession.Round, reached via Room.ActiveGame: GameSession option. It was kept rather than removed purely so existing code/tests that reference it don't need churn for zero functional gain (per its doc comment in backend/Domain/Game.fs).

Verify it

  • task dotnet:build / task frontend:build — both must build clean.
  • Open two browser tabs, join World chat with different names in each — confirm both see each other in the roster (including whichever one joined first — that's the RoomPlayers snapshot doing its job) and that chat messages appear in both.
  • See Testing for the automated coverage.
