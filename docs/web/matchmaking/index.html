Feature

Random matchmaking

Play someone random: wait for the next available player, or be paired immediately with whoever is already waiting.

One queue, not two features

Waiting for a random player and joining an open game are the two halves of a single queue, so they are one hub method rather than two. Whether you wait or are matched depends entirely on who happens to be queued at that instant — splitting it would turn that into a race the client has to resolve, and the client cannot know the answer.

The queue is ordered oldest-first, so whoever has waited longest is matched first rather than an arbitrary player being picked. It is room-scoped: a player waiting in one room is never matched with someone in another.

What cannot happen

A player is never matched with themselves, never matched into a second game while already in one, and never matched with someone who has since left — a queue entry does not outlive its player. That last rule is enforced in removePlayers, the single choke point every removal path goes through: voluntary leave, the stale-disconnect sweep, and same-name rejoin alike.

A player holds at most one place in the queue, so asking again with different settings updates their entry rather than queueing them twice.

Which settings the game uses

The waiting player's. They chose first, and the joiner opted into "whatever is open" rather than a particular game, so the settings travel with the queue entry and the game that starts is the one the waiting player actually asked for.

Starting the game

A match starts the game through the same RoundStarted broadcast as any other game — there is no separate "matched" event, because that message already carries everything a client needs. A matched game has no play request behind it, so the client resolves its opponent from the session itself; without that the game screen would never mount for either player.

Implementation

The queue lives on the room as WaitingForMatch, with pure operations in backend/Domain/Game.fs (joinMatchmaking, leaveMatchmaking, findMatchFor) and the hub methods FindMatch/CancelMatchmaking in backend/Api/GameHub.fs. frontend/src/components/bg-room-setup.ts owns the button, the waiting state and the cancel path.

Queue rules are unit tested in backend/Tests/MatchmakingTests.fs; waiting, pairing and cancelling end to end in frontend/e2e/matchmaking.spec.ts, which uses private rooms so a player left waiting by another test cannot match this one's first player instantly.
