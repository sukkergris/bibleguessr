Feature

Links and navigation

Every screen has its own address, so a shared link leads straight to it, a reload stays put, and the browser's Back and Forward buttons move between screens.

The addresses

Address Screen
/ The front page.
/play/the-bible, /play/books, /play/chapters A singleplayer game type's setup screen.
/multiplayer Create or join a room. Also World chat, which has no code of its own.
/multiplayer/<room code> The join screen with that code filled in — and the address while you're in that room.
/social Social.
/social/daily-quiz Today's daily quiz.
/watch/<room code> The room's spectator board.

A game in progress has no address of its own: a reload during a singleplayer game goes back to that game type's setup screen. An address the app doesn't know shows the front page, and the address bar is corrected to /.

What links lead where

  • A shared daily quiz result ends with /social/daily-quiz — whoever follows it can play today's quiz.
  • A shared singleplayer result ends with its game type, e.g. /play/books.
  • In a room, Share invite link shares /multiplayer/<code>. The link fills in the code; the visitor still picks their Bible and name (both remembered from earlier visits) and presses Join. Nobody joins a room just by opening a link.
  • The Congregation lobby offers /watch/<code> for a projector.

Back, Forward and reload

Every move between screens — a button, a link, ← Home — adds a history entry. Back and Forward show whatever screen the address then names, and leave the current one exactly as its own buttons would: leaving a singleplayer screen drops the game in progress, and leaving a room's address leaves the room, the same as Back to chat selection. Coming Forward to a room's address offers the room again; it doesn't rejoin it.

A reload stays on the same address. In a room, that means the join screen with the code — and, for a Congregation player, rejoining under the same name takes back their seat (see Congregation).

Page titles

Each screen sets the page title, e.g. "Daily quiz — BibleGuessr" or "Room 4821 — BibleGuessr". That is what a screen reader announces after a move, and what the Back button's history menu lists.

The web server must fall back to the app

The addresses are real paths, not # fragments, so the browser asks the server for /social/daily-quiz itself. The server must answer every path that isn't a file, the API or the hub with index.html, and the app takes it from there.

  • Vite — vite dev and vite preview already do this, and the server replica proxies everything else to Vite.
  • nginx serving the built files — the location that serves the frontend needs a fallback: 
    location / {
    root /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
}
    The built page refers to its scripts and styles by absolute paths (/assets/…), so it works at any depth.
Check production before relying on links

Production's frontend serving config isn't in this repository. Until it falls back to index.html, a shared deep link answers 404 there, while the front page keeps working.

Implementation

frontend/src/routing/routes.ts is the one place that knows the addresses: Route (a union with one case per screen), routeFromPath, its inverse pathOf, urlOf for full links, and titleOf. All pure and unit tested.

frontend/src/routing/navigation-controller.ts is a Lit reactive controller owned by <bg-app>. It reads the address on load, adds history entries in navigate(), follows popstate, sets the title, and turns a plain click on an ordinary <a> to one of the app's own addresses into an in-page move — so links can be real links. Links with a target, a modifier key or a middle-click are left to the browser.

<bg-app> renders the screen for the current route. A singleplayer game's own stage (setup, playing, results) lives beside it, and any change of route resets it. Areas with screens of their own stay unaware of addresses:

  • <bg-social-home> shows the view it is given and asks for another with social-view-requested, which keeps Social free of the app shell (see Social). It is handed the daily quiz's link for shared results.
  • <bg-room-setup> takes the address's room code as routeRoomCode and reports room-entered and room-left.

Adding an address

  1. Add a case to Route in routes.ts.
  2. The compiler then points at pathOf, titleOf and <bg-app>'s _renderScreen. Add the path to routeFromPath yourself — and a row to routes.test.ts, which checks that every route reads back from its own path.
  3. Navigate to it with navigate(), or link to it with an ordinary <a>.

Tests

  • frontend/src/routing/routes.test.ts — every address both ways, stray slashes, unknown addresses, titles.
  • frontend/e2e/url-navigation.spec.ts — a daily quiz link, Back and Forward, game type addresses, unknown addresses, in-page links, and room links: the invite link, joining from it, Back leaving the room.
