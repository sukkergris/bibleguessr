Feature

Player presence

A live connection-status dot next to each player, an "Offline" section for disconnected players (unable to be invited), automatic removal after 2 minutes of being disconnected, and remembering your name per browser. See docs/SCRUM/Feature.ConsiderTimeoutForDisconectedPlayers.md.

Builds on Multiplayer rooms & chat.

The problem this solves

Originally, nothing in the hub ever removed a player from a room — closing a tab or losing the connection left a stale entry sitting in the roster forever, unclickable-but-visible junk. This feature fixes that without being harsh about it: a brief network drop or a page refresh shouldn't make someone vanish from the roster mid-conversation.

The design

  1. Immediate — visible, but not invitable: the instant a connection drops, the player is marked disconnected. They move into a separate Offline section of the roster (still visible — a brief drop shouldn't make someone vanish from the conversation), but any invitation involving them is cancelled right away, and they can no longer be clicked to send a new one — see Unique player names for the sibling feature this one builds directly on.
  2. After a grace period: if they haven't reconnected within Room.disconnectGracePeriod = 2 minutes, a periodic sweep removes them for real, and every other client's roster updates live.
  3. Reconnect before the timeout: rejoining under the exact same name moves the player back to Online — see the callout further down for how this is actually implemented (a same-name rejoin, not true session resume).

Backend

Domain functions

backend/Domain/Game.fs

Function What it does
markDisconnected playerId at room Records playerId → at in Room.DisconnectedPlayers. Does not remove them from Players.
cancelPendingRequestsFor playerId room Drops any pending invitation naming playerId (sent or received) — the instant they disconnect, not waiting for the grace period. Leaves Players, DisconnectedPlayers, and ActiveGame untouched — this is the one thing that DOES change immediately on disconnect, everything else waits. Returns (updatedRoom, cancelledRequests) so the caller knows which withdrawn/denied-equivalent event to broadcast per request.
markReconnected playerId room Clears a pending disconnection. Still unused by any hub code path — see the callout below for why (same-name rejoin via prepareJoin is what actually satisfies "reconnect before the timeout," not this function).
removeStaleDisconnections cutoff room Removes every player disconnected before cutoff, along with any play requests they sent or received (already-cancelled ones from cancelPendingRequestsFor included, harmlessly — there's nothing left to drop for them by this point). Returns (updatedRoom, removedPlayerIds).

GameHub.OnDisconnectedAsync

backend/Api/GameHub.fs

On disconnect: drops the connection→player mapping, then — inside one atomic RoomStore.Update call — both Room.markDisconnected (with DateTimeOffset.UtcNow) and Room.cancelPendingRequestsFor run together, not as two separate updates. Broadcasts PlayerDisconnected, then PlayRequestWithdrawn (the disconnecting player was the sender) or PlayRequestDenied (they were the target) for each cancelled request — the exact same events/payload shapes WithdrawPlayRequest/ DenyPlayRequest already send for an explicit withdraw/deny, so the frontend needed zero new event handling.

Why one atomic update, not two

A second, separate rooms.Update call for cancelPendingRequestsFor would reopen a real race window between "marked disconnected" and "requests cancelled" — e.g. AcceptPlayRequest landing in that gap and starting a game against someone who'd already disconnected. Every room-state change in this hub goes through RoomStore.Update's compare-and-swap retry loop for exactly this reason (see backend/Tests/RoomStoreConcurrencyTests.fs — a real lost-write bug, unrelated to this feature, that this rule was written to prevent from recurring).

PlayerCleanupService

backend/Api/GameHub.fs — registered via AddHostedService in Program.fs

A BackgroundService that sweeps every PresenceSettings.SweepInterval (30 seconds by default): for each room, computes cutoff = UtcNow - PresenceSettings.DisconnectGracePeriod, calls Room.removeStaleDisconnections, and broadcasts PlayerLeft for each player actually removed.

Both values are configurable

PresenceSettings (backend/Api/GameHub.fs) is a small record — { DisconnectGracePeriod: TimeSpan; SweepInterval: TimeSpan } — read from Presence:DisconnectGracePeriodSeconds / Presence:SweepIntervalSeconds in backend/Api/Program.fs (plain seconds, matching this file's existing Smtp:Port convention — not a TimeSpan string), each defaulting to the previous hardcoded value (2 minutes / 30 seconds) when unset. Registered as a DI singleton and injected into PlayerCleanupService's constructor, same pattern as MailSender.SmtpSettings. The point isn't runtime tuning for a real deployment — it's letting a developer dial BOTH values down to a couple of seconds for manual verification (e.g. via environment variables: Presence__DisconnectGracePeriodSeconds=2 Presence__SweepIntervalSeconds=1, then start task dotnet:dev), so an actual disconnect→removal round-trip can be watched end-to-end in a few seconds instead of the real 2-minute wait, without touching production code or its defaults. Room.disconnectGracePeriod itself is untouched — it's still the domain-level default value PresenceSettings falls back to, and what backend/Tests/DisconnectCleanupTests.fs asserts directly.

This is deliberately not wired into an automated e2e test: Playwright never starts or configures the backend in this codebase (see frontend/playwright.config.ts's own doc comment — it's always an already-running task dotnet:dev process, whatever config that happens to have), so a suite test built around this override would only pass when a developer happened to have started the backend with it set — either silently skipped or, worse, hanging for a real 2 minutes against a normally-started one. The actual removal LOGIC already has full, always-run coverage via backend/Tests/DisconnectCleanupTests.fs's injected cutoff parameter (which doesn't go through this config path at all); this override's job is manual/exploratory verification of the live wiring, not automated regression coverage.

Events

Event Fires when Frontend effect
PlayerDisconnected immediately, connection drops player moves from the Online section to Offline; no longer clickable to invite
PlayRequestWithdrawn / PlayRequestDenied immediately, if the disconnecting player had a pending invitation (sent or received respectively) — same events an explicit withdraw/deny already send, see OnDisconnectedAsync above the invitation disappears from the other party's UI live, exactly like an explicit withdraw/deny
PlayerLeft after the 2-minute sweep removes them player removed from the roster and from any play requests involving them

Frontend

frontend/src/components/chat-panel.ts partitions players into two sections — Online and Offline — by whether each id is in disconnectedPlayerIds: Set<string>, an unambiguous per-player server truth distinct from this viewer's own connectionState (which is only about being uncertain about your own connection, and still renders inline in Online). bg-room-setup.ts adds to disconnectedPlayerIds on PlayerDisconnected and, on PlayerLeft, removes the player from the roster/play-request lists and clears them from the disconnected set. The Offline section only renders when non-empty.

Within Online, the existing .status-dot (green = connected, grey = this viewer's own connection is uncertain) still applies. Offline rows drop the dot entirely — the section itself already says "offline" — and are rendered greyed out with no class="clickable" and no @click handler at all, structurally rather than via a runtime guard: there's simply no click target for an offline player, so nothing can invite them. bg-room-setup.ts's _onPlayerSelected also checks disconnectedPlayerIds itself as defense in depth, for the narrow race where a click could land a frame before a PlayerDisconnected re-render removes the handler.

(A future random-matchmaking feature — docs/SCRUM/Feature.ConnectToRandomNextOpenGame.md, not yet built — must exclude DisconnectedPlayers from its candidate pool the same way invitations are excluded here; noted in backend/Domain/Game.fs's own doc comment so it isn't forgotten when that feature gets built.)

Remembering your name

frontend/src/player-name-storage.ts

loadRememberedPlayerName() / saveRememberedPlayerName(name), backed by localStorage (key bibleguessr:playerName). Pre-fills the name input on the multiplayer screen and saves on a successful join. This is a per-browser convenience only, not an identity — the server still mints a fresh PlayerId on every join regardless. Both functions swallow localStorage errors (private browsing, storage disabled) and just degrade to "nothing remembered" rather than breaking the join flow.

No PlayerId session resume — but same-name reconnect is handled

A player who reconnects (refreshes, or their connection recovers) always gets a brand-new Player/PlayerId — there's still no session-resume mechanism, and there's still deliberately no "PlayerReconnected" event. Room.markReconnected remains unused by any hub code path today.

That said, reconnecting under your own name is no longer a dead end the way it once was. Unique player names' Room.prepareJoin gives it real, useful handling at the roster level: if your old connection is still sitting in DisconnectedPlayers when you rejoin under the same name, that stale entry (and its pending play requests/active game) is silently removed first, so the rejoin succeeds cleanly under a fresh id instead of either being rejected as a duplicate name or leaving a second, ghost entry behind. What's still missing is resuming the old PlayerId itself — score, in-progress game state, and anything else keyed by the old id don't carry over to the new one.

That handling only covers a genuinely dropped connection, though — prepareJoin checks DisconnectedPlayers, and nothing marks you disconnected while your tab is still open. A player who deliberately leaves (clicks "← Home") without their connection ever actually dropping needed a separate fix: Unique player names' Room.leave / GameHub.LeaveRoom now removes a voluntary leaver immediately, unconditionally — see that page's "Leaving a room voluntarily" section for the bug this closes (rejoining your own still-open room, same tab, same name, used to be rejected as a duplicate).

Verify it

  • Backend: backend/Tests/DisconnectCleanupTests.fs — mark/reconnect/sweep semantics, the 2-minute disconnectGracePeriod value itself, and cancelPendingRequestsFor's full behavior (drops a request naming the disconnecting player on either side, leaves unrelated requests and the disconnecting player's own Players/ ActiveGame untouched, handles multiple requests targeting the same player, no-ops when there's nothing to cancel).
  • End-to-end: frontend/e2e/player-presence.spec.ts — closes one browser context and confirms the other player moves into an Offline section live (no longer clickable) while still visible (the grace period), and confirms the remembered name survives a page reload. frontend/e2e/play-request.spec.ts — a pending invitation disappears live for the other party the instant either the sender or the target disconnects, without waiting for the grace period. frontend/e2e/unique-player-name.spec.ts — a same-name rejoin lands back in Online for a bystander watching. None of these drive the real 2-minute removal end-to-end (that would mean an actual wait in the test) — that path is covered by the backend unit tests instead.
