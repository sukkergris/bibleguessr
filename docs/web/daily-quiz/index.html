Feature

Daily quiz

Every day at 00:00 UTC the server draws five random verses from the whole Bible and stores them in a small SQLite database. Everyone who plays that day gets the same five, from Social.

What the player sees

  • Social → Play today's quiz first asks which Bible to play from — a server translation (the default) or the player's own file — with the same picker as multiplayer. Start today's quiz is enabled once the choice is valid (e.g. an uploaded file has finished parsing). Then the quiz shows the day's date and "Verse 1 of 5".
  • Every verse's text, and the guess form's book names, come from the chosen Bible. If it doesn't have one of the day's verses (a different verse numbering, a book left out), the quiz says "This verse isn't in your Bible." and offers Skip this verse, for no points — instead of the whole quiz failing.
  • At the top, a countdown to the next quiz ("Next quiz in 05:12:47"), counted to the next 00:00 UTC in the browser — midnight UTC is the same moment everywhere, so the server needn't send it. Once the day has moved past the quiz on screen it says "A new quiz is ready." with a Play the new quiz button; it never swaps the quiz itself, so a game in progress is never interrupted. It is a role="timer", which screen readers don't announce on every tick.
  • Each verse is guessed with the usual guess form (any book) and scored by the standard rules — see Scoring. After each guess the feedback shows the points and the right answer; the next-verse button takes focus, so Enter carries on.
  • After the fifth verse: today's total and each verse's result, then Back to Social.
  • Share result shares a short text: the quiz's date, the total, verse by verse which parts were right (✅, a green check) or not (❌, a red cross) with that verse's points, when it was played (date and time, in UTC like the quiz itself) and a link to the game — e.g.

    A part counts as right by the same rule as the points (the shared kernel's correctParts): the chapter only when the book is right too, the verse only when both are, and a part not guessed isn't right. A verse missing from the player's own Bible shows as skipped. The column header and the marks' different shapes mean the result doesn't rest on color alone. It is written like every share in the app (see Scoring), and the link is the address the game is served from, so it follows the environment. It opens the device's own share menu where there is one (phones, mostly) and copies the text to the clipboard otherwise, saying so in a status line. Canceling the share menu does nothing. The text deliberately leaves the verses out, so it doesn't give today's answers away to someone who hasn't played yet (and verse text never leaves the device).
  • Nothing about the player is saved: playing again replays the same five verses.

How a day's quiz is made

  1. DailyQuizScheduler (backend/Api/DailyQuizService.fs) makes the day's quiz at startup and then at every 00:00 UTC.
  2. If that ever didn't happen — the server was down at midnight, say — GET /api/daily-quiz makes it on the day's first request instead (DailyQuizService.getOrCreate).
  3. Either way a day gets exactly one quiz: storing a second one for the same day is refused (INSERT OR IGNORE on the day's primary key), and whoever lost that race reads the stored one. A day's quiz never changes, also across restarts.

The rules are pure functions in backend/Domain/DailyQuiz.fs: which UTC day a moment belongs to, when the next one starts, and drawing a number of distinct verses (the same verse in two translations counts once). The randomness is passed in, so the draw is testable. Each verse has a 20% chance of being one of the famous verses — see Famous verses.

References only, never verse text

The database and the endpoint carry only book number, chapter and verse number (plus the server's own book spelling for display). Each player looks the text up from their own source, the same way a multiplayer round does. See "Data security" in CLAUDE.md.

The database

One SQLite file, opened through Microsoft.Data.Sqlite — no database server. It suits the setup: a single API process, which also holds rooms and games in memory.

Setting Database:FilePath (env Database__FilePath)
  • Schema: backend/Api/Database.fs holds an ordered list of migrations, applied once each at startup; the version reached is kept in SQLite's own PRAGMA user_version. A schema change is a new entry, never an edit of an old one. Tables: daily_quizzes (one row per day) and daily_quiz_verses (its verses, in order).
  • WAL mode: the database file has two companions, -wal and -shm. Keep all three together.
  • Backup: unlike /data/bibles, the /data/db volume can't be recreated from the image — keep it across deploys and back it up. While the API runs, don't copy the file; use sqlite3 bibleguessr.db ".backup backup.db". With the API stopped, copying the files is fine.
"Today's quiz couldn't be loaded (404)"

The backend serving the page predates the daily quiz: /api/daily-quiz doesn't exist in it. Restart it (check with /api/revision). nginx needs no change — it forwards everything under /api/.

Frontend

The quiz lives in Social (frontend/src/social/daily-quiz/): daily-quiz-client.ts fetches the day's quiz, daily-quiz-session.ts is the flow as an explicit state model (choosing a Bible → loading → playing → finished, or failed; while playing, the current verse is being looked up, shown, or not in the chosen Bible), daily-quiz-game.ts renders it with the shared verse card and guess form (frontend/src/shared-ui/) and the shared Bible picker (frontend/src/bible-sources/), and next-quiz-countdown.ts is the countdown and daily-quiz-share.ts builds the shared text (the session records when the quiz was finished, for its time).
