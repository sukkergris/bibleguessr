Feature

Multi-platform images

Both Docker images are published as one multi-platform manifest list covering linux/amd64 and linux/arm64, under the same names and tags as before.

Why this exists

The production server is arm64 and has no emulation, so an amd64-only image fails with exec format error. Apple Silicon development machines are arm64 too, and pulling an amd64-only image there prints a platform-mismatch warning and runs under QEMU. With a manifest list, Docker pulls the variant that matches the host automatically. The deploy repository needs no changes.

How the images are built

Image Build stage Final stage
bibleguessr-api FROM --platform=$BUILDPLATFORM .NET SDK. It runs natively on the builder and cross-publishes with dotnet publish -a $TARGETARCH (the RID becomes linux-musl-x64 or linux-musl-arm64). aspnet runtime, one per target platform. It runs as apiuser (UID 1000).
bibleguessr-nginx FROM --platform=$BUILDPLATFORM Node. Vite runs once, natively. Its output is platform-independent static files. The official multi-arch nginx Alpine image, one per target platform.

Only the short RUN steps in the final stages (apk upgrade, adduser, mkdir) execute under QEMU for the non-native platform. The compilers never run emulated.

One build path

build/docker-compose.build.yml is the only place that names the images, their tag, their build args and their Dockerfiles. docker buildx bake reads that compose file directly, so the multi-platform build doesn't need a second copy of any of it. Taskfile.Docker.yml adds only the platforms, from its IMAGE_PLATFORMS variable:

Task What it does Used by
task docker:build:multi Builds both images for every platform in IMAGE_PLATFORMS. Nothing is pushed. ci.yml, job docker-build
task docker:publish:app Runs the same build and pushes one manifest list per image. release.yml, job docker-publish
task docker:build:app (and :api, :nginx) Uses docker compose build for the host platform only and loads the result into the local image store, tagged local (HOST_IMAGE_TAG) instead of the release version. A single-architecture build therefore never overwrites a multi-platform release tag locally, and it cannot be mistaken for a release if pushed. local is used instead of latest because Docker resolves an untagged pull or run to latest. Local testing

Both workflow jobs set up QEMU (docker/setup-qemu-action) and a buildx builder (docker/setup-buildx-action) and then call the task. A workflow runs the same command a developer runs locally.

Things to know about the bake path

The tasks run from build/ and pass --allow=fs.read=... By default, bake refuses a build context outside the current directory. From build/, .. is exactly the repository root, which is the compose file's context.

There is no GitHub Actions build cache. type=gha needs a runtime token that a plain run: step does not receive. Every CI build therefore starts cold, which costs a few minutes. Adding a cache would mean replacing the task call with docker/bake-action, which would split the build back into two paths.

Like every compose-based task, the tasks need DOCKER_USERNAME, BUILD_SHA and BUILD_CONTEXT in the environment. The workflows set all three as job environment variables. Locally, DOCKER_USERNAME and BUILD_CONTEXT come from the git-ignored .github/workflows/.vars, which the root Taskfile.yml loads as a dotenv file, or from your shell. You set BUILD_SHA yourself. Taskfile.Docker.yml must not redeclare these three in its env: block: a '{{.VAR}}' template there cannot see dotenv values, so it would overwrite them with empty strings.

Building locally on any host

The same task builds both platforms on an arm64 host (Apple Silicon) and on an amd64 host (Intel/AMD). The non-native platform's final stages run under QEMU, as in CI. The host needs two things: QEMU binfmt handlers for the other architecture, and a builder that can produce multi-platform images.

Host One-time setup
Docker Desktop (macOS, Windows, any CPU) None. Docker Desktop ships QEMU, and its default builder uses the containerd image store, which holds multi-platform images.
Docker Engine on Linux

Install QEMU handlers for the other architecture (repeat after a reboot unless your distribution persists them):

docker run --privileged --rm tonistiigi/binfmt --install all

Then create a builder that supports multi-platform builds, because the default docker driver does not unless the containerd image store is enabled:

docker buildx create --name multi --driver docker-container --use

Check with docker buildx ls that the active builder lists both linux/amd64 and linux/arm64.

Create .github/workflows/.vars with DOCKER_USERNAME and BUILD_CONTEXT (it is git-ignored, so each developer has their own), then build both platforms without pushing: 

BUILD_SHA=$(git rev-parse --short HEAD) task docker:build:multi

With the docker-container driver, the result stays in the builder's cache and is not loaded into docker images. That is enough to prove that both architectures build. Use task docker:build:app for a host-platform image that you want to run, for example isuperman/bibleguessr-api:local.

Verifying

Build both platforms locally without pushing, with every variable given inline:

DOCKER_USERNAME=isuperman BUILD_SHA=local BUILD_CONTEXT=local task docker:build:multi

After a release, confirm that each published tag lists both platforms:

docker buildx imagetools inspect docker.io/isuperman/bibleguessr-api:<tag>
docker buildx imagetools inspect docker.io/isuperman/bibleguessr-nginx:<tag>

Alternative: native arm64 runners

Instead of QEMU, each platform could build on its own runner (runs-on: ubuntu-24.04-arm). The per-platform digests would then be merged with docker buildx imagetools create. This is not the default. Because the heavy stages already run natively, the gain is small, and arm64 runner availability for private repositories depends on the GitHub plan.
