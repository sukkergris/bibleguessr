Site configuration

Settings that differ between deployments live in JSON files the browser reads at startup — not in the code, and not baked into the build.

The files

The frontend reads them with site-config-loader:

  • frontend/public/config/environmentVariables.json — always read. These are production's values.
  • environmentVariables.<environment>.json next to it — read on top, outside production, if it exists. Its settings win.

The environment is whatever <meta name="environment-name"> says — nginx can inject it, as the server replica does with local — or else follows from the host name: localhost is local, a dev., test. or staging. host is development, testing or staging, and anything else is production.

environmentVariables.local.json holds just {}: local runs use production's values. It exists because the dev server answers a missing file with the app page, which the loader would otherwise warn about on every load.

siteUrl https://bibleguessr.uk The site's public address, which canonical links point at (see Search engines). Just the address, with no path.

How the app reads it

frontend/src/site-config/load-site-config.ts reads the files once, on first use, and shares the result. site-config.ts checks it and turns it into a typed SiteConfig; nothing else sees the raw JSON. Nothing waits for it: the first screen renders straight away, and what depends on a setting picks it up when it arrives. If the files can't be read or a setting is invalid, the problem is logged and the app carries on without it — a page then simply has no canonical link.

The package ships no type declarations, so site-config-loader.d.ts declares the part the app uses.

Serving and caching

Vite serves frontend/public/config/ at /config/ and copies it into the build. In the nginx image, server-replica/nginx/includes/static-assets.conf serves /config/ from the built files and lets browsers cache it for 47 minutes, so a changed setting can take that long to reach a returning visitor. For a change that must land at once, deploy it under a new file name — the loader takes a custom base name.

Adding a setting

  1. Add it to SiteConfig and check it in siteConfigFrom, with a test.
  2. Give production's value in environmentVariables.json.
  3. Use it from loadSiteConfig(), without holding up the first screen.

Tests

  • frontend/src/site-config/site-config.test.ts — what counts as a valid configuration, and that the one production ships is.
  • frontend/e2e/seo.spec.ts — canonical links follow a different configured address, and a page without a configuration still works.
