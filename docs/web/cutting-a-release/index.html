Procedure

Cutting a release

The checklist for shipping a release: which of three version values to edit, in what order, and the one edit that's easy to forget because it doesn't follow the same rule as the other two.

Scope

This is the practical checklist — what to touch and in what order. Versioning explains why the three values are independent and never meant to match each other, and Application release covers what the release workflow itself does once the tag lands. Read this one first if you just want to ship.

Three values, one release

A release touches up to three separately-edited values, and only one of them is required every time:

  • frontend/package.json's version — edit only if the frontend changed.
  • BackendVersion in backend/Api/Program.fs — edit only if the backend changed.
  • the returned value in scripts/ci/load-image-version.sh — edit every release, whether or not either application changed.
The third one isn't optional

Both Docker images are rebuilt and republished on every tag push, regardless of what triggered the release. Skipping the load-image-version.sh edit doesn't skip the publish — it just means the new images silently overwrite whatever tag the script last returned, instead of publishing under their own. This is the mistake this checklist exists to prevent.

The checklist

  1. Test the change thoroughly first. Nothing below should happen before you're confident the commit you're about to tag is the one you want to ship.
  2. If the frontend changed, bump version in frontend/package.json .
  3. If the backend changed, bump BackendVersion in backend/Api/Program.fs .
  4. Every time, regardless of the two steps above: edit the returned value in scripts/ci/load-image-version.sh to something new, following the project's n.n.n form (e.g. 1.1.0 ).
  5. Commit and push whichever of the three files you actually changed — the two application-version files are omitted if their application didn't change, but scripts/ci/load-image-version.sh is always in the commit.
  6. Tag the pushed commit frontend-v<version> , matching frontend/package.json , and push the tag. The tag is the release trigger — see Application release for what runs afterward and how to watch it.

Why the third value works differently

frontend/package.json 's version and BackendVersion are each their application's own semantic version — they change when that application's behavior changes, and nothing else. The value scripts/ci/load-image-version.sh returns is a different kind of thing: a deployment coordinate for the pair of Docker images built from this commit, not either application's version. It doesn't need to match either bump above, or follow any particular scheme beyond being new — but it does need to actually be new, every time, because both images publish under it unconditionally.

See Versioning: Bumping a version for the full reasoning behind keeping the three values independent.

A worked example

task release:bundle
git add frontend/package.json backend/Api/Program.fs scripts/ci/load-image-version.sh
git commit -m "release: frontend v0.8.3"
git push origin main
git tag frontend-v0.8.3
git push origin frontend-v0.8.3
gh run watch

Omit the two application-version files from git add if their application didn't change this time — scripts/ci/load-image-version.sh stays in either way. This is the same example used in Application release ; it's repeated here so the checklist above and the actual commands sit next to each other.

Implementation

frontend/package.json , backend/Api/Program.fs and scripts/ci/load-image-version.sh are the three files this checklist edits. .github/workflows/main.yml is what a pushed frontend-v* tag triggers — Application release covers that workflow in full.
