Procedure

Cutting a release

The checklist for shipping a release: which of three version values to edit, in what order, and the one edit that's required every time because it names the release itself.

Scope

This is the practical checklist — what to touch and in what order. Versioning explains why the two application revisions are independent of the release version, and Application release covers what the release workflow itself does once the tag lands. Read this one first if you just want to ship.

Three values, one release

A release touches up to three separately-edited values, and only one of them is required every time:

  • frontend/package.json's revision — edit only if the frontend changed.
  • BackendRevision in backend/Api/Program.fs — edit only if the backend changed.
  • the returned value in scripts/ci/load-image-version.sh — the release version. Edit it every release, whether or not either application changed.
The third one isn't optional

The release version is the git tag (v<version>), the GitHub release and the tag of both Docker images. The check-tag job in the release workflow refuses to run unless the pushed tag is exactly v followed by what load-image-version.sh returns, so a forgotten edit fails the run before anything is built or published instead of silently overwriting the previous images.

The checklist

  1. Test the change thoroughly first. Nothing below should happen before you're confident the commit you're about to tag is the one you want to ship.
  2. If the frontend changed, increment revision in frontend/package.json .
  3. If the backend changed, increment BackendRevision in backend/Api/Program.fs . Both can be done with task release:revision -- frontend backend (name only the side that changed).
  4. Every time, regardless of the two steps above: edit the returned value in scripts/ci/load-image-version.sh to the new release version, in the project's n.n.n form (e.g. 0.0.2 ).
  5. Commit and push whichever of the three files you actually changed — the two revision files are omitted if their application didn't change, but scripts/ci/load-image-version.sh is always in the commit.
  6. Tag the pushed commit v<release version> , matching scripts/ci/load-image-version.sh , and push the tag. The tag is the release trigger — see Application release for what runs afterward and how to watch it.

Why the third value works differently

frontend/package.json 's revision and BackendRevision are plain integer counters, one per application — incremented by one when that application changes, and nothing else. They are for humans: a counter that did or did not move tells you at a glance which side a release changed. The value scripts/ci/load-image-version.sh returns is a different kind of thing: the version of the release as a whole — one number for the tag, the GitHub release and the pair of Docker images built from this commit. It doesn't need to match either application revision, but it does need to be new every time, because each release is published under it.

See Versioning: Bumping a version for the full reasoning behind keeping the application revisions independent of the release version.

A worked example

task release:bundle
git add frontend/package.json backend/Api/Program.fs scripts/ci/load-image-version.sh
git commit -m "release: v0.0.1"
git push origin main
git tag v0.0.1
git push origin v0.0.1
gh run watch

Omit the two revision files from git add if their application didn't change this time — scripts/ci/load-image-version.sh stays in either way. This is the same example used in Application release ; it's repeated here so the checklist above and the actual commands sit next to each other.

Implementation

frontend/package.json , backend/Api/Program.fs and scripts/ci/load-image-version.sh are the three files this checklist edits. .github/workflows/release.yml is what a pushed v<n.n.n> tag triggers, and scripts/ci/check-release-tag.sh is its first job's guard — Application release covers that workflow in full.
