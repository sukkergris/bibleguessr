Feature

Connection status

The dot in the upper-right corner, what it actually measures, and how quickly it can be trusted.

The panel

Clicking the dot opens a small Connection status panel. The heading also names the group for assistive technology, so the rows are announced as belonging to something rather than read bare.

Three independent signals

The indicator combines three things that can disagree, and deliberately keeps them separate in the details panel:

  • This device — navigator.onLine, whether the machine itself reports having a network.
  • /api/healthz — a periodic GET, showing round-trip latency when it succeeds, with the base URL alongside it because that is the useful part when diagnosing a port-forwarding gap. The countdown to the next check sits in this row, so the reader can tell how old the latency figure is rather than guessing.
  • Realtime (SignalR) — the hub connection's own state, reported through its onclose, onreconnecting and onreconnected callbacks.

The endpoint was renamed from /api/health to /api/healthz; the old path still responds, so anything already polling it keeps working.

How the rows and the dot relate

Each row is an explicit state object carrying its own ok flag, and the dot is derived from those same objects — red when any row is red. The two therefore cannot disagree. This replaced a set of separate getters that had to be kept consistent by hand, and were not: the dot ignored the device row entirely, so a machine with no network showed a green dot directly above a row reading "offline".

There are exactly two colours. Red means something is wrong; green means nothing is. A grey "not applicable" state was tried for the realtime row and dropped — a third colour asks the reader to learn a vocabulary in a panel they open precisely because they want a quick answer. Where no hub connection exists, nothing is broken, so the row is green and the text carries the fact that it is not in use.

What the dot says

The status is text, not colour alone. The first failing row names the problem, so the dot reports the most specific thing it knows rather than a generic failure: No network on this device, Server unreachable, Reconnecting…, Disconnected, or Connected. It appears in the button's accessible name and its tooltip, so it is available to a screen reader and to anyone who cannot distinguish the colours.

A local network drop reporting as No network on this device rather than Server unreachable matters: the latter blamed the server for a problem on the player's own machine.

Reconnecting… is kept distinct from Disconnected because they mean different things to a player: one is "hold on", the other is "this is not working".

How quickly it reacts

Three mechanisms, in descending order of how much they matter:

  • The browser's offline/online events trigger an immediate re-check. This is what makes the indicator feel responsive — measured at roughly a millisecond, against 15.2 seconds before it existed.
  • Adaptive polling — 15 seconds while healthy, 3 seconds while not. A working server does not need poking, but someone who has just lost their connection is watching the dot and wants to know when it returns.
  • SignalR callbacks fire as soon as the hub itself notices, which is prompt for a clean close but not for a silent network failure.

navigator.onLine is treated strictly as a hint that something changed, never as truth: it says whether the machine has a network, not whether this backend is reachable. It prompts a real check rather than being reported as a state.

Known limits

These are real and worth knowing before trusting the dot as a diagnosis:

  • SignalR is only tracked in the multiplayer room. Elsewhere the realtime row reads "not used on this screen" and the dot reflects the other two signals — correct, since no hub connection exists to be broken, but it means the dot is a weaker signal outside multiplayer. The row is green there because nothing is wrong, not because a check has passed; the wording is what distinguishes the two.
  • A silent network failure is not detected instantly without an offline event. A WebSocket can stay apparently open until keep-alive expires. If connectivity is lost in a way the browser does not report — a server that stops responding while the network stays up — detection still falls back to the polling interval.
  • Healthy polling is 15 seconds. A backend that fails without any browser-level signal can appear healthy for up to that long.

Implementation

frontend/src/components/connection-status.ts owns the indicator, the adaptive polling and the status text. frontend/src/signalr-client.ts reports the hub state, including the reconnecting case. frontend/src/components/bg-app.ts decides when realtime tracking is enabled.

Prompt reaction, accessible status text and recovery are covered by frontend/e2e/connection-status.spec.ts, verified by removing both fixes and confirming all three tests fail.
